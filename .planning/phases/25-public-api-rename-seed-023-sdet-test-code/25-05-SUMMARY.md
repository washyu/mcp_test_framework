### Implementation deviation (D-18 noqa scope)

**Plan said:** Apply D-18 exclusion markers liberally on legitimate compat-shim lines.

**Reality:** The plan 06 leak gate (next wave) is line-by-line (per the Task 2/3 verifier scripts in this plan). A noqa marker at the closing `"""` of a docstring does NOT cover the prose lines above it — the regex scanner reads each line independently. I therefore tagged the per-line shim definitions explicitly: `config.py`'s AliasChoices block (4 lines), the model_validator method docstring + body (8 lines), the `model_validate` override docstring + body (4 lines), the `_check_legacy_sdet_key_in_yaml` helper (6 lines), the `cli.py` `sdet_legacy` shim block (4 lines), the `_runner.py` parameter + docstring (4 lines), the `sdet/__init__.py` shim file (3 lines).

Two non-functional follow-ups:
- The existing `# noqa: E402, sdet-rename-shim` in `sdet/__init__.py:18` was re-ordered to `# noqa: sdet-rename-shim, E402` so the substring check `'noqa: sdet-rename-shim' in line` matches. Behaviorally identical for both noqa tokens (the codes are unordered in standard noqa parsers).
- The README HTML-comment sentinel before the captured CLI snapshot deliberately mentions the snapshot's contents (`"(SDET)" header, "Judges: (none — SDET scope)" line, "mcp_test_framework.sdet.errors.ToolCallError" rows`). The single comment carries the noqa marker so the whole sentinel line passes the gate; the snapshot block itself is left intact for Phase 30 re-capture. The sentinel is the single-line tagging mechanism that prevents Phase 30 from having to re-introduce noqa markers on every internal snapshot line if it chooses to defer the re-capture.

This is not a Rule 4 architectural change — D-18 is honored in spirit (legitimate shims tagged); the *granularity* of tagging is what the implementation found necessary for the line-by-line gate.
