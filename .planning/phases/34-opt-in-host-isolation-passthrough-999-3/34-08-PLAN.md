## Host isolation: strict vs passthrough

By default (`host_isolation: strict`), the framework spawns the MCP server subprocess with an isolated env — allowlist + tempdir HOME redirect + null keyring backend — so test runs are reproducible and your operator host's credentials never leak into a subprocess under test.

Some live-stack scenarios need the opposite. The 2026-05-19 worked example: an operator has Proxmox credentials in their keyring (`uvx homelab-mcp credentials list` confirms), wants the framework to drive a `homelab-mcp create_proxmox_vm` scenario, but under strict mode the spawned subprocess sees `No Proxmox credentials found` because the null-keyring backend hides them.

Opt into passthrough mode:

```yaml
# config.yaml
host_isolation: passthrough  # operator's real env reaches the MCP subprocess
test_code:
  generated_root: tests/test_code/_generated
```

Run as usual:

```bash
$ uv run mcp-contracts run

# Under host_isolation: strict (default):
homelab-mcp create_proxmox_vm  →  FAIL: No Proxmox credentials found

# Under host_isolation: passthrough:
homelab-mcp create_proxmox_vm  →  PASS: VM created
```

Passthrough disables pytest-xdist parallelism. The framework clamps worker count to 1 with this banner:

```
[mcp-contracts] xdist worker count clamped to 1

host_isolation=passthrough serializes subprocess spawns so the operator's credentials remain a single-owner resource.

next: switch to host_isolation=strict for parallel xdist runs
```

**Locks (read before opting in):**
- **SEED-022 — operator owns safety.** The framework does not reason about which tools or env vars are "dangerous". Passthrough hands the spawned subprocess your full environment; you choose which scenarios to run.
- **No keyring faking.** The framework will not synthesize credentials or virtualize the keyring. Passthrough delegates fully to your actual host environment.
- **xdist parallelism trade-off.** Strict mode preserves `-n N` worker counts; passthrough clamps to 1.
```
