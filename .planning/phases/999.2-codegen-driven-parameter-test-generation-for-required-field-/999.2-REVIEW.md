# Phase 999.2: Code Review Report

**Reviewed:** 2026-05-26
**Depth:** standard
**Files Reviewed:** 12
**Status:** issues_found

## Summary

Phase 999.2 adds codegen-driven smoke-scenario emission for required-field MCP tools: a new `examples` field on `ToolConfig`, the `_emit_smoke_scenario()` pure-data emitter appended to `_codegen.py`, wiring through `generate()` and the CLI, end-to-end tests, and operator-facing docs.

The core logic is sound: `json.dumps()` escaping is applied correctly in all three branches (single, multi, TODO/skip), and the import-before-skip ordering in the TODO branch is correct and verified. The `getattr(tool_cfg, 'examples', None)` duck-typed access handles None, missing-attr, and non-list-attribute cases without crashing (though non-list examples from rogue shims produce semantically broken generated code — see WR-02).

One blocker is identified: `examples/homelab-mcp.yaml` uses the `sdet:` key which was removed in v1.5, making the file fail to load against the current framework and contradicting its own header comment. Three warnings cover a missing Pattern D test assertion, the validator's bracket-vs-dot error message discrepancy for non-list iterables, and the missing smoke-file count in the CLI summary. Three info items cover the cosmetically misleading indentation in the single-example branch, the unnecessarily broad `# noqa: F401` in real-scenario branches, and test file duplication.

## Critical Issues

### CR-01: `examples/homelab-mcp.yaml` uses the removed `sdet:` key — file fails to load

**File:** `examples/homelab-mcp.yaml:40`
**Issue:** The worked reference config uses `sdet:` as the top-level key for the generated-root config block. The `sdet:` key was removed in v1.5 (the same release this phase targets). Loading this file with the current framework raises a `ValidationError` with two errors: `('test_code',) Field required` and `('sdet',) Extra inputs are not permitted`. The CLI's `_emit_operator_error_for_validation` maps the `sdet:` shape to a pointer telling operators to rename the key — so an operator who copies this file verbatim immediately hits that exact error. The inline comment at lines 35–39 says "Either `sdet:` ... or `test_code:` ... loads into the same model" and "The legacy `sdet:` key emits a one-shot DeprecationWarning ... and is removed in v1.5" — but then the file uses `sdet:` anyway. The comment's intent was apparently to document the back-compat alias, but the alias no longer exists, making both the file and the comment actively misleading.

**Verified:** `uv run python -c "from mcp_test_framework.config import Config; Config(yaml_file='examples/homelab-mcp.yaml')"` raises `ValidationError`.

**Fix:**
```yaml
# examples/homelab-mcp.yaml — replace lines 35–41:

# test-code codegen + fixture output path. REQUIRED.
# ...
test_code:
  generated_root: "tests/test_code/_generated"
```

Also update the generated_root value from `tests/sdet/_generated` to `tests/test_code/_generated` to match the v1.4 rename. Remove the inline comment about the back-compat alias — that history belongs in a changelog, not in an operator-facing reference file that new operators copy verbatim.

## Warnings

### WR-01: Missing Pattern D assertion in `test_config_example.py` — examples field not pinned

**File:** `tests/framework/unit/test_config_example.py:117` (after last test)
**Issue:** `test_config_example.py` tests Pattern A (`judges`), Pattern B (`call_arguments`), and Pattern C (`skip: true`, `skip_reason`) with dedicated structural assertions. Pattern D, which is the new addition this phase introduces (the `examples:` + `skip_buckets: ["output"]` pairing), has no corresponding structural assertion. The only coverage for Pattern D is:
- `test_config_example_has_placeholder_tools` checks that the `<required_field_tool>` key is present in the `tools:` block.
- `test_config_example_has_pattern_comments` checks that "Pattern D" appears as text.

Neither test verifies that `<required_field_tool>` actually has an `examples:` field or a `skip_buckets:` field. A future edit that accidentally removes the `examples:` block from `config.example.yaml` or renames it to `example:` (typo) would not be caught by any test.

**Fix:**
```python
def test_config_example_pattern_d_has_examples_and_skip_buckets() -> None:
    """Pattern D = required-field tool with examples: + skip_buckets: pairing."""
    data = _load()
    d = data["tools"]["<required_field_tool>"]
    assert "examples" in d, (
        "Pattern D entry must demonstrate the examples: field "
        "(codegen-driven smoke scenario -- Phase 999.2)"
    )
    assert isinstance(d["examples"], list) and len(d["examples"]) > 0, (
        "Pattern D examples: must be a non-empty list of argument dicts"
    )
    assert "skip_buckets" in d, (
        "Pattern D entry must demonstrate the skip_buckets: pairing "
        "(recommended companion to examples: for required-field tools)"
    )
```

### WR-02: `_validate_examples_shape` bracket-index error message bypassed for non-list iterables

**File:** `src/mcp_test_framework/models.py:151-183`
**Issue:** The `mode="before"` validator's operator-tone error message — `"examples[{i}] must be a mapping..."` — only fires when `v` is already a `list`. For non-list iterables that Pydantic coerces to a list (tuples, generators, range objects), the validator's `isinstance(v, list)` check is `False` at the time the before-validator runs, so it returns `v` unchanged. Pydantic then coerces the iterable to a list and validates each item using its own type machinery, producing a dot-notation error (`examples.1`) rather than the promised bracket-notation error (`examples[1]`).

```python
# Reproduction:
ToolConfig(examples=({'vmid': 9001}, 42))
# Error loc: ('examples', 1)  <-- Pydantic dot notation
# Expected:  examples[1]      <-- validator bracket notation
```

This matters primarily for Python-API callers rather than YAML-file operators (YAML parses `[]` as `list`, so the before-validator always sees a list from YAML). However, the validator's docstring explicitly promises that it "fires BEFORE Pydantic's own list-item coercion" — that promise is only true for list inputs. The validator comments describe a behavior contract that is not uniformly upheld.

**Fix:** Add an explicit tuple/sequence coercion at the top of the validator before the `isinstance(v, list)` check, or broaden the check:

```python
@field_validator("examples", mode="before")
@classmethod
def _validate_examples_shape(cls, v: Any) -> Any:
    if v is None:
        return v
    # Coerce tuple/other sequences to list so the for-loop below fires
    # for any sequence type, not just list. YAML always produces list,
    # but Python-API callers may pass tuples.
    if not isinstance(v, (list, dict)):
        try:
            v = list(v)
        except TypeError:
            return v  # let Pydantic's own type error handle non-iterables
    if not isinstance(v, list):
        return v  # dict case: let Pydantic's type-rejection handle it
    for i, item in enumerate(v):
        if not isinstance(item, dict):
            raise ValueError(
                f"examples[{i}] must be a mapping of argument-name to "
                f"argument-value; got {type(item).__name__}"
            )
    return v
```

### WR-03: `gen-test-classes` CLI output does not report smoke file emission count

**File:** `src/mcp_test_framework/cli.py:1408-1416` and `src/mcp_test_framework/test_code/_codegen.py:617-698`
**Issue:** The `generate()` function emits `<tool>_call_smoke.py` for every required-field tool but returns only `{"tools": N, "degraded_fields": M}` — smoke files are not counted. The `gen_test_classes` CLI command echoes `"tools: N generated"` without mentioning how many smoke files were written (including how many are real scenarios vs TODO/skip placeholders). An operator who runs `gen-test-classes` after adding `examples:` entries to their config.yaml has no visible confirmation that smoke files were emitted.

```
# Current CLI output (3 tools, 1 with examples):
gen-test-classes: wrote test-code classes for homelab-mcp
  server:    homelab-mcp v0.5.2
  slug:      homelab_mcp
  target:    tests/test_code/_generated/homelab_mcp/
  tools:     3 generated
  degraded:  0 fields (grep "codegen: degraded" for details)
  # No mention of smoke files at all.
```

**Fix:** Add `smoke_scenarios` and `smoke_todos` to the counts dict returned by `generate()`, and surface them in the CLI output:

```python
# In generate():
counts = {"tools": 0, "degraded_fields": 0, "smoke_scenarios": 0, "smoke_todos": 0}
# ...
smoke_source = _emit_smoke_scenario(...)
if examples:  # real scenario branch
    counts["smoke_scenarios"] += 1
else:          # TODO/skip branch
    counts["smoke_todos"] += 1

# In gen_test_classes():
typer.echo(
    f"  smoke:     {counts['smoke_scenarios']} scenario(s), "
    f"{counts['smoke_todos']} placeholder(s) "
    f"(add examples: to config.yaml to promote placeholders)"
)
```

### IN-01: Single-example branch generates visually misleading indentation in `params =` line

**File:** `src/mcp_test_framework/test_code/_codegen.py:773-785`
**Issue:** In the single-example branch (Branch A), the `json.dumps(examples[0], indent=4)` call produces a multi-line dict literal with 4-space indentation from column 0. When embedded directly into the f-string as `{params_cls}(**{example_lit})`, the dict body appears at column 0 inside a function body that is indented 4 spaces. The result is syntactically valid Python but visually misleading:

```python
# What is generated:
    params = CreateVmParams(**{
    "vmid": 9001,          # <-- looks like it's at function scope
    "name": "smoke-test-vm"
})                         # <-- closing at column 0
    response = await tool("create_vm").call(params)
```

The code is syntactically valid (Python does not enforce indentation inside dict literals) and all tests pass, but a developer reading the generated file would be confused about the indentation structure. The multi-example branch (`_EXAMPLES = {examples_lit}`) does not have this problem because the assignment is at module scope.

**Fix:** Use `textwrap.indent` to add consistent indentation to the dict body relative to the `params =` line:

```python
import textwrap
example_lit = json.dumps(examples[0], indent=4)
# Re-indent so the dict body aligns with the opening brace (8 spaces for function body + opening)
indented_lit = textwrap.indent(example_lit, "    ")
# Then embed as:
#     params = CreateVmParams(**{indented_lit})
```

Or emit the pattern differently to avoid the multi-line dict inline entirely:
```python
f"    _EXAMPLE = {example_lit}\n"
f"    params = {params_cls}(**_EXAMPLE)\n"
```

### IN-02: `# noqa: F401` on preamble import line is overly broad in real-scenario branches

**File:** `src/mcp_test_framework/test_code/_codegen.py:754`
**Issue:** All three branches share the same preamble, which includes:
```python
from mcp_test_framework.test_code import mcp_session, tool  # noqa: F401
```
The `# noqa: F401` is correct for the TODO/skip branch (both `mcp_session` and `tool` are imported but the module skips before they are used). In the real-scenario branches (single and multi), `tool` IS used in the generated body (`await tool(...).call(params)`), so the `F401` suppression for `tool` is unnecessary. For `mcp_session`, it appears as a fixture parameter — flake8/ruff don't know it's used by pytest fixture injection, so `# noqa: F401` is still appropriate there.

The suppressor is broad (silences F401 for the entire line) and will mask a genuine unused import if a future edit removes the `tool(...)` call from the template without also updating the import.

**Fix:** The cleanest approach: use per-symbol suppression in the real-scenario preamble, or split the preamble for the real-scenario branches:
```python
from mcp_test_framework.test_code import mcp_session  # noqa: F401 -- pytest fixture
from mcp_test_framework.test_code import tool
```
However, given all three branches share a single `preamble` string, the simplest fix is to document the suppression intent more precisely in a comment:
```python
"from mcp_test_framework.test_code import mcp_session, tool  # noqa: F401 -- mcp_session is a pytest fixture\n"
```

### IN-03: `_ToolCfgShim` duplicated across two test files with no shared fixture

**File:** `tests/framework/unit/test_codegen_smoke_emitter.py:52-61` and `tests/framework/unit/test_codegen_emitter.py:241-243`
**Issue:** The `_ToolCfgShim` duck-typed stand-in for `ToolConfig` is defined identically in both test files. The comment in `test_codegen_smoke_emitter.py` explicitly notes the duplication: "Duplicated here so each test file is self-contained (no shared fixture, no conftest coupling)." This is a deliberate design choice and the duplication is intentional. However, the two definitions are not byte-identical (`test_codegen_emitter.py` omits the docstring and type annotation on `__init__`), so they can drift independently.

**Fix:** If the "self-contained" philosophy is worth preserving, pin the duplication with an assertion comment noting both files must stay in sync. If sharing is acceptable, move to a `tests/framework/unit/conftest.py`:
```python
# tests/framework/unit/conftest.py
import pytest

class _ToolCfgShim:
    """Duck-typed stand-in for ToolConfig -- only needs .examples."""
    def __init__(self, examples=None):
        self.examples = examples

@pytest.fixture
def tool_cfg_shim():
    return _ToolCfgShim
```
