## User Constraints (from CONTEXT.md)

### Locked Decisions

- **D-01:** Operator example values live in `config.yaml` only — under `tools.<name>.examples:` as a **list of example argument dicts**. `pyproject.toml`, `inputSchema.examples`, and dual-surface overlays are rejected.
- **D-01a:** `examples:` is a **new field on `ToolConfig`**, distinct from the existing `call_arguments:` (the output-bucket field stays as-is). The two fields do NOT alias each other.
- **D-01b:** Schema: `examples: list[dict[str, Any]] | None = None`. Pydantic validation rejects non-list, non-dict items. Each example dict's keys are **not** validated against `inputSchema.required` at config-load time — runtime concern of `<ToolName>Params(**example)`.
- **D-02:** For a required-field tool with no `examples:`, `gen-test-classes` STILL emits `<tool>_call_smoke.py` — a TODO scenario that calls `pytest.skip(reason="no examples; populate tools.<name>.examples: in config.yaml to enable this smoke")` at module top. The scenario is fully importable (no NameError on Params).
- **D-02a:** Skip reason text MUST be grep-able and include the exact config path `tools.<name>.examples:`.
- **D-03:** `gen-test-classes` **unconditionally overwrites** any existing `<tool>_call_smoke.py`. Every generated file carries a header sentinel matching the existing `<tool>.py` style verbatim.
- **D-03a:** Header line matches existing `<tool>.py` so a single grep across `_generated/` finds both kinds for cleanup/regen.
- **D-04:** This phase does **not** add any config-level linkage between `examples:` and `skip_buckets`. Independent operator surfaces. (SEED-022 — framework does no tool-safety reasoning.)

### Claude's Discretion

- Generated file path: `tests/test_code/_generated/<server>/<tool>_call_smoke.py`. Reuse existing `<server>` directory layer from `<tool>.py` emission.
- Scenario shape: single `@pytest.mark.asyncio` test function named `test_<tool>_call_smoke`. `len(examples) > 1` → `pytest.mark.parametrize` (one ID per example).
- `exclude_unset=True` source: use the existing `_tool_factory.py` serializer path (no new serializer code).
- Required-field detection: `len(tool.inputSchema.get("required", [])) > 0`. Tools with `required: []` or missing `required` get NO smoke file (zero-output).
- CLI surface: no new flag on `gen-test-classes`. Emission is part of the existing command's normal output.

### Deferred Ideas (OUT OF SCOPE)

- New `mcp-contracts list-required` CLI subcommand
- `examples ↔ skip_buckets` config-level linkage
- Reading `examples` from `pyproject.toml` or `inputSchema.examples`
- Hand-edit-preserving merge logic for `<tool>_call_smoke.py`
- Hash-based regen skip / `--force` overwrite gating

## Summary

Phase 999.2 extends the existing pure-data emitter in `src/mcp_test_framework/test_code/_codegen.py` (entry point: `generate()`) and the CLI driver in `src/mcp_test_framework/cli.py` (entry point: `gen_test_classes` Typer command, calling `_codegen.generate(...)` at line 1391). The emitter currently knows nothing about config — it operates only on `(server_name, server_version, tools, out_root, timestamp)`. The cleanest implementation hands a new `tools_config: dict[str, ToolConfig]` kwarg into `generate()` so the per-tool emission branch can read `examples`. The CLI already has `cfg.tools` in scope at the `generate()` call site.

The new `<tool>_call_smoke.py` files sit **inside** `_generated/<server>/` next to their `<tool>.py` sibling. Because they live inside the generated package, they can use a **relative import** (`from .<tool> import <ToolName>Params`) — they do NOT need to know the operator's project package path. This is critical: the generated scenarios must be portable across operator project layouts (the existing `mcp_session` fixture loads `_generated/<slug>/__init__.py` via `importlib.util.spec_from_file_location` with `submodule_search_locations=[str(slug_dir)]` precisely so the generated package's relative imports work — see `src/mcp_test_framework/test_code/session.py:97-101`).

The serializer surface is already complete: `tool("name").call(params)` at `src/mcp_test_framework/test_code/_tool_factory.py:101` calls `params.model_dump(mode="json", exclude_unset=True)`. The generated scenario just constructs `<ToolName>Params(**example)` and awaits the call; the Phase 24 `exclude_unset=True` semantics are inherited for free. No serializer changes.

**Primary recommendation:** Plumb `tools_config` into `_codegen.generate()`, add a sibling `_emit_smoke_scenario(tool, tool_config) -> str | None` pure function returning either the scenario source or `None` (when `required: []`), and write the emitted file alongside `<tool>.py` in the existing per-tool loop. Add `examples` to `ToolConfig` with a single `field_validator` mirroring the Phase 33 `_no_duplicate_buckets` idiom.

### Pattern 1: ToolConfig field + validator (Phase 33 WR-01 idiom)

**What:** Add `examples` field to `ToolConfig` matching the existing `skip_buckets` validator style.
**When to use:** ANY new operator-facing field on `ToolConfig`.
**Example:**
```python
# src/mcp_test_framework/models.py (additions to ToolConfig)

examples: Optional[list[dict[str, Any]]] = Field(
    default=None,
    description=(
        "Example argument dicts the codegen uses to drive "
        "tests/test_code/_generated/<server>/<tool>_call_smoke.py. "
        "Each example becomes one parametrized scenario invocation. "
        "Keys are NOT validated against inputSchema.required at config "
        "load — that surfaces at runtime as a Pydantic ValidationError "
        "when <ToolName>Params(**example) is constructed inside the "
        "generated scenario."
    ),
)

@field_validator("examples", mode="after")
@classmethod
def _validate_examples_shape(
    cls, v: Optional[list[dict[str, Any]]]
) -> Optional[list[dict[str, Any]]]:
    """Reject non-list / non-dict-item shapes at config load time.

    D-01b: load-time validation is shape-only. Per-example key validation
    against the tool's inputSchema.required is a RUNTIME concern (the
    generated scenario constructs <ToolName>Params(**example), which
    raises ValidationError if a required key is missing — surfacing as
    a test failure rather than a config error).
    """
    if v is None:
        return v
    # Pydantic typing already coerces, but be explicit for the operator-tone
    # error path (mirrors _no_duplicate_buckets at models.py:117-137).
    for i, item in enumerate(v):
        if not isinstance(item, dict):
            raise ValueError(
                f"examples[{i}] must be a mapping of argument-name to "
                f"argument-value; got {type(item).__name__}"
            )
    return v
```
**Source:** Phase 33 WR-01 commit (702a586) at `src/mcp_test_framework/models.py:117-137` — `_no_duplicate_buckets`.

### Pattern 2: Pure-data emitter + I/O-owning driver (existing codegen split)

**What:** `translate_tool(...)` returns a source string; `generate(...)` owns `shutil.rmtree` + `write_text`. The new smoke emitter MUST follow this split.
**When to use:** Every new emission slot in `_codegen.py`.
**Example:** Add `_emit_smoke_scenario(tool: Tool, examples: list[dict[str, Any]] | None) -> str | None` as a pure function (returns `None` for `required: []`, returns source string otherwise). `generate(...)` checks the return and writes the file alongside `<tool>.py`. See `_codegen.py:617-669` for the existing loop site.

### Pattern 3: Relative-import shape inside `_generated/<slug>/`

**What:** Generated `__init__.py` already uses `from .<tool> import <ToolName>Params, <ToolName>Response`. The new smoke scenario follows the same relative-import convention.
**When to use:** Any new file emitted inside `_generated/<slug>/` that references sibling generated modules.
**Why critical:** The `mcp_session` fixture loads `__init__.py` via `spec_from_file_location` with `submodule_search_locations=[str(slug_dir)]` (`session.py:97-101`). Relative imports resolve via this mechanism. An absolute import like `from tests.test_code._generated.homelab_mcp import ...` would fail because (a) it depends on the operator's project package path, and (b) the generated package is loaded as a synthetic `_mcptf_test_code_generated_<slug>` module (`session.py:94`), NOT as the operator-visible Python package.
**Verified:** `tests/test_code/_generated/homelab_mcp/__init__.py:19` shows `from .create_proxmox_vm import CreateProxmoxVmParams, CreateProxmoxVmResponse`.

### Anti-Patterns to Avoid

- **Absolute import in the smoke scenario:** `from tests.test_code._generated.homelab_mcp.create_proxmox_vm import CreateProxmoxVmParams` — breaks for operators with a different project layout and breaks the `mcp_session` synthetic-package loader. Use relative `from .create_proxmox_vm import CreateProxmoxVmParams`.
- **Bare `@pytest.mark.asyncio`:** Will hang at the first `await` because `mcp_session` is session-scoped and the bare marker binds the test to a new loop. MUST use `@pytest.mark.asyncio(loop_scope="session")` (verified `docs/TEST-CODE-AUTHORING.md:139,152-156`).
- **Calling `params.model_dump()` inside the generated scenario:** Pass the `<ToolName>Params` instance directly to `tool().call(params)`; the wrapper's `.call()` calls `model_dump(mode="json", exclude_unset=True)` itself (`_tool_factory.py:101`). Pre-dumping inside the scenario would lose the `exclude_unset` semantics.
- **Adding `examples` to `call_arguments`:** D-01a explicitly forbids this. The two fields stay distinct.
- **Validating `example.keys() == inputSchema.required` at config load:** D-01b explicitly forbids this — runtime concern.
- **New `--force` / hash-check on the smoke emitter:** D-03 is unconditional overwrite. Adding any gating logic re-litigates the decision.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Serializing `<ToolName>Params` for the wire | A `params.dict()` / `json.dumps(asdict(params))` call inside the generated scenario | `await tool("<name>").call(params)` (calls `model_dump(mode="json", exclude_unset=True)` internally) | Phase 24 `exclude_unset=True` is critical for distinguishing operator-set from operator-omitted fields. Re-implementing loses that. |
| Loading the generated package at scenario import time | A `spec_from_file_location` call in `<tool>_call_smoke.py` | Rely on `mcp_session` fixture (already does the loading) + a relative `from .<tool> import ...` | The fixture's loader is the single source of truth for the synthetic package shape. |

## Common Pitfalls

### Pitfall 1: Forgetting `loop_scope="session"` on the generated marker

**What goes wrong:** Generated `<tool>_call_smoke.py` uses bare `@pytest.mark.asyncio` instead of `@pytest.mark.asyncio(loop_scope="session")`. Every smoke scenario hangs at the first `await` (silently — pytest reports it as a long-running test).
**Why it happens:** Easy copy-paste from generic pytest-asyncio examples; bare marker is more common in the wild.
**How to avoid:** Hardcode `@pytest.mark.asyncio(loop_scope="session")` in the emitter template. Add a framework self-test that greps for the exact string in every emitted smoke file.
**Warning signs:** A smoke scenario "hangs" instead of failing fast on `await`.
**Source:** `docs/TEST-CODE-AUTHORING.md:152-156` documents this exactly.

### Pitfall 2: Absolute import in the smoke scenario breaking under `mcp_session`

**What goes wrong:** Emitting `from tests.test_code._generated.homelab_mcp.create_proxmox_vm import CreateProxmoxVmParams` works in CWD-as-repo-root invocations but breaks (a) for operators using a different `generated_root` and (b) under the `mcp_session` synthetic-package loader (which loads under `_mcptf_test_code_generated_<slug>`, NOT under the operator-visible path).
**Why it happens:** The hand-authored `tests/test_code/test_proxmox_vm_lifecycle_readme_sample.py` uses a custom `spec_from_file_location` loader (lines 60-104) to import `CreateProxmoxVmParams` from the operator's project. That pattern is wrong for files that live INSIDE `_generated/<slug>/`.
**How to avoid:** Always emit `from .<module_name(tool.name)> import <pascal_case(tool.name)>Params` — a relative import. The smoke file lives in the same directory as `<tool>.py`, so the relative import is direct.
**Warning signs:** `ImportError: attempted relative import with no known parent package` (means `submodule_search_locations` was not set — should not happen for files loaded via `mcp_session`, but does happen if the operator tries to run the smoke scenario standalone via `pytest tests/test_code/_generated/<slug>/<tool>_call_smoke.py` without going through the fixture).

### Pitfall 3: `examples:` key collision with `inputSchema.required` discovered too late

**What goes wrong:** Operator writes `examples: [{vmid: 9001, name: smoke-vm}]` but forgets that `inputSchema.required` also lists `node`. Test fails with a Pydantic `ValidationError` referencing the missing key.
**Why it happens:** D-01b says "do not validate at config load." The first signal is the test run.
**How to avoid:** This is intentional per D-01b — not a bug. The generated scenario surfaces the validation error as a clear test failure with the missing key name. Document in the LIBRARY-MODE worked example that operators should run `mcp-contracts list-tools --name <tool> --full` to see the required keys before populating `examples:`.
**Warning signs:** `pydantic_core.ValidationError: Field required [type=missing, input_value=...]` in test output. The error message is operator-readable.

### Pitfall 4: Multi-example parametrize ID instability

**What goes wrong:** Emitter derives parametrize IDs from example values (e.g. `f"vmid-{example.get('vmid')}"`), so when the operator changes an example value the test ID changes — pytest history / `--lf` / `-k` filters break.
**Why it happens:** Heuristic IDs feel "nicer" than positional ones.
**How to avoid:** Use positional `ids=[f"example-{i}"]` for `i in range(len(examples))`. Operators who want named scenarios can drop the smoke file and hand-author a scenario (the documented escape hatch — D-03 rationale).
**Warning signs:** None visible until an operator notices `--lf` re-runs the wrong scenario.

### Pitfall 5: `examples` field declared but `_codegen.generate()` never reads `cfg.tools`

**What goes wrong:** The Pydantic field validates correctly, but no smoke scenario references the examples. The smoke files emit but always with the `pytest.skip(...)` TODO branch.
**Why it happens:** The CLI driver at `cli.py:1391` currently calls `_codegen.generate(server_name=..., server_version=..., tools=..., out_root=...)` with no `tools_config` parameter. Adding the field to `ToolConfig` is independent of plumbing it into `generate()`.
**How to avoid:** Add a `tools_config: dict[str, ToolConfig] | None = None` kwarg to `generate()`, thread `cfg.tools` from `cli.py:1391`, AND add a framework self-test that asserts the examples-present branch emits a real scenario (not the TODO branch) when `tools_config` carries an entry.
**Warning signs:** Framework self-tests pass for the validator + emitter independently, but a manual run shows every smoke file is the TODO variant.

### Pitfall 6: `<tool>.py` does NOT exist for tools with `required: []` — wait, it does

**What goes wrong (potential):** Emitter logic assumes `<tool>.py` always exists as an import target for `<tool>_call_smoke.py`. If `_codegen` ever stops emitting `<tool>.py` for tools with no properties, the smoke file's relative import breaks.
**Why it does NOT happen today:** `_emit_params_body` at `_codegen.py:421-455` emits a `pass`-body class even for tools with no properties (the `class CreateProxmoxVmParams(BaseModel): pass` form). Every tool the server advertises produces a `<tool>.py`. The smoke emitter gates separately on `len(required) > 0` — the gate is independent of `<tool>.py` existence.
**How to avoid:** Add a framework self-test that confirms `<tool>.py` is emitted for tools with `required: []` (regression guard against future codegen changes). One already exists implicitly at `test_codegen_emitter.py:34-44` (the `_t()` factory creates tools with empty `required`).

## Failure Modes / Open Questions

### Resolved during research

1. **Does `<tool>.py` exist for tools with `required: []`?** YES — `_emit_params_body` at `_codegen.py:421-455` emits a `pass`-body class for non-property schemas. The smoke emitter can safely gate on `len(required) > 0` independent of `<tool>.py` existence.

2. **When `inputSchema.required` mentions a key NOT in `inputSchema.properties`?** Existing `_format_field_line` / `_emit_params_body` skip that key silently (`_format_param_signature` at `cli.py:1576-1577` does `if name in props:` before emitting). Translation: the resulting `<ToolName>Params` class will NOT have the missing key as a field, so `<ToolName>Params(**example)` will succeed even if the example sets the missing key — but `extra="forbid"` (`_codegen.py:544`) will then reject the extra field. **Recommendation:** Don't special-case this; let the runtime `ValidationError` surface (operator gets a clear "Extra inputs are not permitted" error). The smoke emitter does not need to inspect this case.

3. **Per-server subdir naming for unusual server names:** `server_slug()` at `_slugs.py:24-47` already handles every case (loud-fail on empty / all-non-identifier). Reuse it.

4. **Parametrize IDs: stable index vs heuristic?** RECOMMEND positional `f"example-{i}"`. Heuristic IDs (e.g. derived from `vmid` value) break `pytest --lf` and `-k` filters when operator edits an example. Documented as Pitfall 4.

### Genuinely open for the planner

5. **Where should the smoke-emitter source string live — same `_codegen.py` module, or a sibling `_smoke_codegen.py`?**
   - What we know: `_codegen.py` is 670 lines and already mixes pure-data emission with I/O. Adding `~80 lines` for the smoke emitter keeps it in one place but pushes the file toward 750 lines.
   - What's unclear: project convention on file size / single-responsibility split.
   - Recommendation: Keep it in `_codegen.py` for the MVP — colocates the I/O loop (`generate()`) with the new emitter function. Split to `_smoke_codegen.py` ONLY if the smoke emitter grows beyond ~100 LOC. Less risk of broken-import surface across the rest of the test-code package.

6. **Should `pytest.skip(..., allow_module_level=True)` go BEFORE or AFTER the `from .<tool> import <ToolName>Params` import in the TODO branch?**
   - What we know: `allow_module_level=True` aborts module collection immediately. Putting the import BEFORE skip means an `ImportError` on `<ToolName>Params` would surface as a collection error rather than a skip.
   - What's unclear: whether D-02's "fully importable" intent means "the module bytes load" or "every import in the module executes successfully."
   - Recommendation: Put the import BEFORE the skip — matches D-02 spirit ("scenario must still be importable") and gives the operator a real error if `<tool>.py` is missing (which would indicate a codegen bug, not an example-content issue). Use `# noqa: F401` to document the unused import.

7. **Should `_emit_smoke_scenario` accept the full `ToolConfig` or just `examples: list[dict[str, Any]] | None`?**
   - What we know: Per-tool emission only needs `examples`.
   - What's unclear: whether future smoke-emitter knobs (e.g. operator-facing scenario name override) belong on `ToolConfig`.
   - Recommendation: Accept just `examples` for now — narrow signature, easy to test. If a second knob arrives, switch to passing the `ToolConfig` instance.
