# Phase 999.2: Codegen-driven parameter-test generation for required-field tools - Context

**Gathered:** 2026-05-26
**Status:** Ready for planning

<domain>
## Phase Boundary

Extend the existing `mcp-contracts gen-test-classes` CLI to emit, in addition to the per-tool `<ToolName>Params` Pydantic class it already writes, a typed SDET scenario file `tests/test_code/_generated/<server>/<tool>_call_smoke.py` for **every tool whose `inputSchema.required` array is non-empty**. The generated scenario constructs `<ToolName>Params(**example)` from operator-supplied `examples:` values in `config.yaml` and calls the tool through `tool("<name>").call(params)` using the Phase 24 `exclude_unset=True` serializer.

**In scope:**
- Codegen extension to `gen-test-classes` (no new CLI subcommand)
- New `tools.<name>.examples:` config field (list of example arg dicts) with Pydantic model + schema validation
- Generated `<tool>_call_smoke.py` file emission with `# DO NOT EDIT` header sentinel and `pytest.skip()` placeholder when examples are absent
- Docs touch: README + `docs/LIBRARY-MODE.md` snippet showing the workflow (required-field tool → `examples:` block → generated scenario)

**Out of scope:**
- New `mcp-contracts list-required` subcommand (adjacent capability — separate phase)
- Pydantic linkage between `examples:` and `skip_buckets: ['output']` (decided D-04 below: independent surfaces)
- Reading examples from `pyproject.toml` or `inputSchema.examples` (decided D-01: config.yaml only)
- Hand-edit-preserving merge logic (decided D-03: unconditional overwrite)
- Auto-modifying `config.yaml` to add `skip_buckets` (rejected as SEED-022 violation)

</domain>

<decisions>
## Implementation Decisions

### Examples source

- **D-01:** Operator example values live in `config.yaml` only — under `tools.<name>.examples:` as a **list of example argument dicts**, e.g.:

  ```yaml
  tools:
    create_proxmox_vm:
      examples:
        - vmid: 9001
          name: smoke-test-vm
          node: pve1
          cores: 2
          memory: 2048
        - vmid: 9002
          name: smoke-test-vm-min
          node: pve1
  ```

  The list shape supports multiple parametrized scenarios per tool. `pyproject.toml`, `inputSchema.examples`, and dual-surface overlays are explicitly rejected to keep the operator-edit surface to a single file.

- **D-01a:** `examples:` is a **new field on `ToolConfig`**, distinct from the existing `call_arguments:` (which is consumed by the deterministic output-conformance bucket with empty-default semantics). The two fields do NOT alias each other — `call_arguments:` stays as-is for v1.5 contract tests; `examples:` is the new codegen-input surface.

- **D-01b:** Schema: `examples: list[dict[str, Any]] | None = None`. Pydantic validation rejects non-list, non-dict items. Each example dict's keys are **not validated against `inputSchema.required` at config load time** — that's the runtime concern of `<ToolName>Params(**example)` inside the generated scenario (Pydantic will raise there if a required key is missing, surfacing as a test failure rather than a config error).

### Missing-examples policy

- **D-02:** For a required-field tool with no `examples:` in config, `gen-test-classes` still emits `<tool>_call_smoke.py` — a **TODO scenario** that calls `pytest.skip(reason="no examples; populate tools.<name>.examples: in config.yaml to enable this smoke")` at module top. The scenario is fully importable (no NameError on Params), so the test-code surface stays clean and the operator sees scaffolding immediately. Filling in examples and re-running `gen-test-classes` replaces the skip with a real call.

- **D-02a:** The skip reason text MUST be grep-able and include the exact config path: `tools.<name>.examples:`. Operators reading skip output should be able to act without consulting docs.

### Regeneration semantics

- **D-03:** `gen-test-classes` **unconditionally overwrites** any existing `<tool>_call_smoke.py`. Every generated file carries the same header sentinel as the existing `<tool>.py`:

  ```python
  # DO NOT EDIT — generated by `mcp-contracts gen-test-classes`
  # Source: <server>'s inputSchema for tool `<tool>` (required: [...])
  # Examples: <N> from tools.<name>.examples: in config.yaml
  ```

  Hash-based change detection, `--force`-gated overwrite, and merge-preserving operator edits are all rejected as over-engineering for v1's pure-codegen contract. Operators who need to customize a scenario beyond `examples:` should write a hand-authored sibling under `tests/test_code/` (existing pattern).

- **D-03a:** The header line matches the existing `<tool>.py` style verbatim so a single grep across `_generated/` finds both kinds of generated files for cleanup or regen.

### Skip-buckets linkage

- **D-04:** This phase does **not** add any config-level linkage between `examples:` and `skip_buckets`. They are independent operator surfaces:
  - Operator may set `examples:` only → codegen scenario fires alongside the (likely-failing) empty-args output-bucket test.
  - Operator may set `skip_buckets: ["output"]` only → output bucket skipped, no codegen scenario emitted (no examples to drive it).
  - Operator sets both → codegen scenario fires, output bucket skipped, schema + judge still run. **This is the recommended pattern**, but the framework does not coerce it.

  Rationale: SEED-022 — framework does no tool-safety reasoning; operator decides what runs. README/LIBRARY-MODE worked example documents the recommended pairing without the validator enforcing it.

### Claude's Discretion

- **Generated file path:** `tests/test_code/_generated/<server>/<tool>_call_smoke.py` per the ROADMAP context. The `<server>` directory layer mirrors the existing `_generated/homelab_mcp/` convention. If the server has a name `gen-test-classes` cannot resolve, use the existing fallback used by `<tool>.py` emission (do not reinvent).
- **Scenario shape:** single `@pytest.mark.asyncio` test function named `test_<tool>_call_smoke`. If `examples:` is a list of length > 1, use `pytest.mark.parametrize` with the list (one parametrize ID per example) — keep scenario count == example count.
- **`exclude_unset=True` source:** use the existing `_tool_factory.py:101` serializer path (`tool().call(params)` already invokes it) — no new serializer code; the codegen output just constructs `<ToolName>Params(**example)` and passes it through. This ensures the generated scenario inherits whatever future serializer changes land.
- **Required-field detection:** the generator inspects `tool.inputSchema["required"]` (already available in the introspection used by the existing codegen). Tools with `required: []` or missing `required` get no `<tool>_call_smoke.py` (zero-output for clarity).
- **CLI surface:** no new flag on `gen-test-classes`. The smoke-scenario emission is part of the existing command's normal output. Operators who currently run the command get the new files automatically on next run (acceptable because `_generated/` is regen-only and the header sentinel makes intent clear).

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `gen-test-classes` CLI in `cli.py` — already does directory-safety checks, refuses to write inside the framework install tree, refuses to overwrite non-empty operator dirs. New emission piggybacks on those guards.
- `<ToolName>Params` Pydantic class emission already exists in `_generated/<server>/<tool>.py` — the new `<tool>_call_smoke.py` just imports `<ToolName>Params` from the sibling file and instantiates it.
- `tool("name").call(params)` in `test_code/_tool_factory.py` — turnkey API for the generated scenario; supports `exclude_unset=True` serialization out of the box.
- `tests/test_code/` is already the documented test-code-author surface; new files land under `_generated/<server>/` per the existing pattern.

### Established Patterns
- **Generated file header sentinel** — every file under `_generated/` carries a `# DO NOT EDIT — generated by ...` first line. New scenarios match exactly.
- **Per-server subdirectory** — `_generated/<server>/` (e.g., `_generated/homelab_mcp/`). New `<tool>_call_smoke.py` sits next to its `<tool>.py` sibling.
- **Pydantic-on-ToolConfig validators** — Phase 33's `WR-01` `field_validator("skip_buckets", mode="after")` for duplicate rejection is the canonical pattern for adding `examples:` validation if any is needed.
- **Single-surface config edits** — Phase 33 deliberately put `skip_buckets` on `ToolConfig` (config.yaml) rather than a side channel. D-01 follows the same instinct.

### Integration Points
- **`gen-test-classes` introspection loop** — wherever the existing code iterates over `discovered_tools` to emit `<tool>.py`, the same loop branches on `len(tool.inputSchema.get("required", [])) > 0` to also emit `<tool>_call_smoke.py`.
- **`ToolConfig` Pydantic model** — adds `examples: list[dict[str, Any]] | None = None` field.
- **`config.example.yaml` + `examples/homelab-mcp.yaml`** — both get a worked `examples:` block (likely `create_proxmox_vm` to match the Phase 33 doc walkthrough — keeps the operator narrative consistent across phases).
- **Test surface** — new framework self-tests under `tests/framework/` covering: required-field tool with examples → real scenario emitted; required-field tool without examples → TODO/skip scenario emitted; non-required-field tool → nothing emitted; multiple examples → parametrize works; header sentinel present; config-load rejects malformed `examples:`.

</code_context>

<specifics>
## Specific Ideas

- **Worked example tool:** `create_proxmox_vm` (the same tool Phase 33 used for its `skip_buckets: ["output"]` documentation). Reusing it across phases gives operators a single narrative thread: "Phase 33 lets you skip the output bucket for `create_proxmox_vm`; Phase 999.2 lets you replace it with a real-args smoke that you parametrize from `examples:`." README + LIBRARY-MODE doc updates should explicitly cross-reference Phase 33.
- **Skip reason text format:** literal `"no examples; populate tools.<tool>.examples: in config.yaml to enable this smoke"` — operator can grep `populate tools.` in pytest output to find every TODO scenario.
- **Header sentinel exact line:** `# DO NOT EDIT — generated by \`mcp-contracts gen-test-classes\`` (backticks around the CLI name; matches existing convention).

</specifics>

<deferred>
## Deferred Ideas

- **`mcp-contracts list-required` CLI subcommand** — Adjacent capability surfaced in the ROADMAP entry. Belongs in its own phase (likely 999.x once the operator runs into the discoverability gap in practice). Captured here so the next backlog review knows it's been considered and intentionally split off.
- **`examples ↔ skip_buckets` config-level linkage** (D-04) — Rejected for this phase on SEED-022 grounds. If operator surveys later reveal frequent mis-configuration (e.g., `examples:` set but `skip_buckets` forgotten), a non-blocking warning could be added in a follow-up phase. Validator-level enforcement remains rejected.
- **Reading examples from `inputSchema.examples`** — Some MCP servers may declare JSON-Schema-standard `examples` arrays. Future phase could add an opt-in "use server-declared examples" mode. For 999.2: operator-only; explicit; predictable.
- **Hand-edit-preserving merge** for `_generated/<tool>_call_smoke.py` — Rejected for v1. If operators consistently need post-codegen edits, the right answer is to lift the scenario out of `_generated/` into a hand-authored sibling, not to teach codegen to merge.
- **Hash-based regen skip** — Same family as merge logic. Defer until churn becomes a measured pain point.

</deferred>
