# Phase 17: Code Review Report

**Reviewed:** 2026-05-12
**Depth:** standard
**Files Reviewed:** 12
**Status:** issues_found

## Summary

Phase 17 ships the codegen surface (walker, file emitter, factory seam, CLI command, pyright gate) plus the Gap-1 conditional-import fix from Plan 17-06. The architecture is coherent — pure-data walker, wipe-and-write emitter, locked seam for Phase 18 — and the test suite is dense.

Adversarial scan surfaces several correctness/safety defects that the test suite does not exercise:

1. **Source-injection via untrusted serverInfo / tool-name strings.** Server-supplied `serverInfo.name`, `serverInfo.version`, and `tool.name` are interpolated directly into generated Python source (header docstring, `__init__.py` registry literal) without escaping. A malicious or buggy MCP server can inject arbitrary Python into the autogenerated files that are then imported by `mcp_session` (Phase 18). The framework treats `homelab-mcp` as a black box subprocess under test — the trust boundary cannot assume well-formed strings.

2. **Field-name codegen has no Python-identifier sanitization.** `_format_field_line` interpolates the JSON-Schema property name verbatim into `    {name}: <type> = Field(...)`. A property named `class`, `import`, `2foo`, or `with space` produces a SyntaxError at import. Slug/module/class helpers all have keyword + leading-digit guards; the field path has none.

3. **Gap-1 fix is itself textually fragile.** `needs_typing = "typing." in body_text` / `needs_field = "Field(" in body_text` scan the entire rendered body, including field-description string literals (rendered via `repr()` into `Field(description='...')`). A field description containing the literal substring `typing.` resurrects the orphaned-import bug Plan 17-06 was meant to close, defeating the pyright-strict gate when the rest of the file genuinely has no `typing.Any` use.

4. **Class-level monkey-patch of `ClientSession.initialize` is process-global.** Acceptable for a single CLI invocation; will silently corrupt state under any future in-process concurrent use (tests, daemonized callers).

Plus minor quality items: dead `_ = (...)` keep-alive, mid-file imports, an unused `name` parameter in `_emit_field`, and inconsistent typing of `_REGISTRY` (`type` vs `type[BaseModel]`).

## Critical Issues

### CR-01: Source injection via unescaped `serverInfo.name` / `version` in generated file headers

**File:** `src/mcp_test_framework/sdet/_codegen.py:43-48`
**Issue:** `HEADER_TEMPLATE` is formatted with `server_name` and `server_version` interpolated into a Python comment without escaping:

```python
HEADER_TEMPLATE = (
    "# AUTOGENERATED by mcp-test-framework gen-sdet-classes -- DO NOT HAND-EDIT.\n"
    "# Source: {slug} (serverInfo.name=\"{server_name}\", version=\"{server_version}\")\n"
    ...
)
```

`server_name` flows directly from `init_result.serverInfo.name` over stdio (`cli.py:1047`). A server that reports `serverInfo.name = 'foo"\n\nos.system("rm -rf ~")\n#'` — or any value containing `"`, `\n`, or `\r` — closes the comment early and injects executable Python into every generated file. Those files are then imported by Phase 18's `mcp_session`, executing the injected code in the test runner's process. The same hazard applies to `server_version`.

The codebase elsewhere acknowledges the threat model: cli.py uses `json.dumps(...)` to defend YAML scalars against malicious tool descriptions. The codegen does not extend the same defense to Python source.

Note: `server_slug` normalization strips dangerous chars from the SLUG (line 47 `_NON_IDENT.sub("_", lowered)`), but the *raw* `server_name` is what lands in the comment. The slug guard does not help here.

**Fix:** Escape both fields before interpolation. The simplest fix is `repr()` minus quotes, or just `json.dumps` for the visible substring:

```python
HEADER_TEMPLATE = (
    "# AUTOGENERATED by mcp-test-framework gen-sdet-classes -- DO NOT HAND-EDIT.\n"
    "# Source: {slug} (serverInfo.name={server_name_repr}, version={server_version_repr})\n"
    "# Regenerated: {timestamp}\n"
    "# Extend by subclassing in tests/sdet/, not by editing this file.\n"
)
# At format-call site:
header = HEADER_TEMPLATE.format(
    slug=slug,
    server_name_repr=json.dumps(server_name),
    server_version_repr=json.dumps(server_version),
    timestamp=timestamp,
)
```

Add a regression test pinning `server_name='evil"\n#'` does not produce invalid/executable Python.

### CR-02: Source injection via unescaped tool name in generated `__init__.py` registry

**File:** `src/mcp_test_framework/sdet/_codegen.py:411-412, 425`
**Issue:** `_render_init` interpolates tool names directly into both `__all__` and `_REGISTRY`:

```python
all_names.extend([f'"{params_cls}"', f'"{response_cls}"'])
registry_lines.append(f'    "{tool_name}": ({params_cls}, {response_cls}),')
```

`tool_name` comes from `tool.name` (line 478, `registry_entries.append((tool.name, ...))`). If a server advertises a tool whose name contains `"` or `\n`, the generated `__init__.py` is malformed — at best a SyntaxError on import, at worst arbitrary code execution (e.g., a tool name of `x", __import__("os").system("..."), "y` closes the string and injects a call into the dict literal).

MCP tool names should match `[A-Za-z_][A-Za-z0-9_]*` per spec, and `cli._yaml_key` already defends YAML against rogue names, but the codegen accepts whatever the server hands it.

**Fix:** Either validate `tool.name` against the MCP-spec regex before emission and raise a `SchemaValidityError` on mismatch, or use `json.dumps(tool_name)` for safe escaping:

```python
registry_lines.append(
    f"    {json.dumps(tool_name)}: ({params_cls}, {response_cls}),"
)
# And reject obviously-malformed names upstream in translate_tool / generate.
```

Add a regression test for a tool name containing a `"` character.

### CR-03: No identifier sanitization on field names — kebab/keyword/leading-digit field names produce invalid Python

**File:** `src/mcp_test_framework/sdet/_codegen.py:263, 282-290`
**Issue:** `_format_field_line` writes the property name verbatim:

```python
lines.append(f"    {name}: {py_type} = {spec.default_expr}")
```

`_emit_params_body` iterates `props` keys with no normalization (`req_names = sorted(n for n in props if n in required)`). JSON Schema property keys are arbitrary strings — they can be:

- Python keywords: `class`, `import`, `for`, `with`, `lambda`
- Leading-digit: `2fa_code`, `403_handler`
- Hyphenated: `vm-id`, `user-name` (common in OpenAPI-derived schemas)
- Whitespace / unicode: `"vm id"`, `"配置"`

Any of these renders syntactically-invalid Python and breaks import of the generated module — taking down the entire SDET surface for that server.

The companion helpers `pascal_case` and `module_name` already implement keyword + leading-digit + non-identifier guards (`_slugs.py:62-95`). The field path has no equivalent.

This is independent of CR-01/CR-02 — those are source-injection; this is "the generated file does not parse." A real-world server with one hyphenated property name fails every Phase 18 test against that server.

**Fix:** Either (a) sanitize the field name and emit a `Field(..., alias='original-name')` so Pydantic still validates the wire field, or (b) degrade the whole tool to `typing.Any` params with a clear comment. Option (a) is the right user surface:

```python
def _safe_field_ident(name: str) -> tuple[str, str | None]:
    """Return (python_ident, alias_if_renamed). alias=None when name was already valid."""
    if name.isidentifier() and not keyword.iskeyword(name):
        return name, None
    # Sanitize using the module_name helper's strategy.
    ident = _NON_IDENT.sub("_", name).strip("_") or "_field"
    if ident[0].isdigit():
        ident = "_" + ident
    if keyword.iskeyword(ident):
        ident = ident + "_"
    return ident, name

# In _format_field_line:
ident, alias = _safe_field_ident(name)
default_expr = spec.default_expr
if alias is not None:
    # Inject alias='<original>' into the Field(...) call.
    default_expr = _inject_alias(default_expr, alias)
lines.append(f"    {ident}: {py_type} = {default_expr}")
```

Add regression tests for each unsafe shape (keyword, leading digit, hyphen, space) against the walker.

### CR-04: Description-string substring scan re-introduces the Gap-1 unused-import bug

**File:** `src/mcp_test_framework/sdet/_codegen.py:350-357`
**Issue:** The Plan 17-06 fix detects whether to emit `import typing` / `Field` by raw substring scan over the rendered body:

```python
body_text = params_body + response_class
needs_typing = "typing." in body_text
needs_field = "Field(" in body_text
```

`body_text` contains the rendered `Field(description=<repr-of-description>)` calls. If a field description contains the literal substring `typing.` (e.g., a docstring like `"Accepts any typing.Any-compatible value"`), `needs_typing` becomes True even though no field actually annotates `typing.Any`. The emitter then writes `import typing` against a body that never references it — exactly the orphaned-import shape that pyright-strict's `reportUnusedImport` rejects, and exactly the bug Plan 17-06 was supposed to close.

This is the same anti-pattern that reviewer issue #5 (FieldSpec.default_is_none) was added to fix on the `default=None` detection path. The fix-by-substring strategy is structurally fragile.

**Fix:** Replace substring scans with structured signals threaded through `FieldSpec` and the emitters. `translate_tool` already knows whether any FieldSpec has `py_type` containing `typing.Any` and whether any field at all was emitted (Field calls). Plumb explicit booleans:

```python
@dataclass(frozen=True)
class FieldSpec:
    ...
    uses_typing_any: bool = False  # True iff py_type references typing.Any

# In _emit_field, set uses_typing_any=True for every degraded path.
# In _emit_params_body / _emit_response_body, return (body, degraded, uses_typing, uses_field).
# In translate_tool, OR the flags and use them directly:
needs_typing = params_uses_typing or response_uses_typing
needs_field = params_has_fields or response_has_fields
```

Add a regression test: a tool with one plain `str` required field whose description literally contains `"typing.Any"` — the generated file must NOT contain `import typing`.

## Warnings

### WR-01: Module-level monkey-patch of `ClientSession.initialize` is process-global, not concurrency-safe

**File:** `src/mcp_test_framework/cli.py:1017-1051`
**Issue:** `_run_codegen_handshake` patches `ClientSession.initialize` at the class level for the duration of the handshake. Two concurrent calls in the same process (e.g., a future test fixture that invokes the helper twice, or any async caller running parallel handshakes) corrupt each other's `holder` capture: both end up reading the same `holder["result"]` slot, and the second `try`/`finally` restores whichever `original_initialize` was captured second. The patch is also visible to ANY other consumer of `ClientSession` in the same process during the window.

The docstring acknowledges this is a workaround for a LOCKED file. Mark it tighter or move to an instance-level patch.

**Fix:** Either gate with a module-level `asyncio.Lock`, or (preferred) patch at the instance level using `types.MethodType` after `__aenter__` exposes the session. If the session isn't reachable before initialize is called, a small contextlib-based guard with a TODO referencing the locked file and a regression test will at least pin the constraint:

```python
import asyncio
_codegen_handshake_lock = asyncio.Lock()

async def _run_codegen_handshake(cfg: Config) -> tuple[object, list[Tool]]:
    async with _codegen_handshake_lock:
        ...  # existing body
```

### WR-02: `_render_init` types `_REGISTRY` value as `type`, not `type[BaseModel]`

**File:** `src/mcp_test_framework/sdet/_codegen.py:419, 422`
**Issue:** The emitted `_REGISTRY` annotation is `dict[str, tuple[type, type[ToolResponse]]]` while `_tool_factory._REGISTRIES` expects `dict[str, tuple[type[BaseModel], type[ToolResponse]]]`. The factory assignment in Phase 18 will pass type-checking only because `type[BaseModel]` is a subtype of `type` — but the generated annotation loses information. pyright-strict accepts this (covariance of `type`), but downstream consumers reading the generated `_REGISTRY` get a weaker type than the factory advertises.

**Fix:** Tighten the generated annotation to match the factory's expectation:

```python
"_REGISTRY: dict[str, tuple[type[BaseModel], type[ToolResponse]]] = {\n"
```

And add `from pydantic import BaseModel` to the rendered `__init__.py` header. Update `test_emitter_init_py_carries_registry` to pin the tighter annotation.

### WR-06: `_check_schema_structural` only runs when input_schema is truthy — empty dict bypasses validation

**File:** `src/mcp_test_framework/sdet/_codegen.py:316-318`
**Issue:**

```python
input_schema = tool.inputSchema if isinstance(tool.inputSchema, dict) else {}
if input_schema:
    _check_schema_structural(tool.name, input_schema)
```

An empty `inputSchema = {}` skips the structural check. That's the intended fast-path, but it also means a schema like `{"required": "not-a-list"}` (no `type`, no `properties`) is silently accepted — `_emit_params_body` returns a `pass` body because `schema.get("type") != "object"`, so the broken `required` field never surfaces. Operators get silent acceptance of a schema the structural check explicitly refuses elsewhere.

This is unlikely to matter in practice (homelab-mcp won't emit such a schema) but inconsistent gating is a code smell.

**Fix:** Always call `_check_schema_structural` when `input_schema` is a dict, even when empty:

```python
input_schema = tool.inputSchema if isinstance(tool.inputSchema, dict) else {}
_check_schema_structural(tool.name, input_schema)
```

The function already short-circuits on non-dict input.

### IN-02: `cli.py:907` `assert cfg is not None` is stripped under `python -O`

**File:** `src/mcp_test_framework/cli.py:907`
**Issue:**

```python
cfg = _load_config(config)  # strict; SAFE-03 fires on absent config
assert cfg is not None, "_load_config(strict) must return Config or raise"
```

Under `python -O` the assert is stripped; the subsequent `cfg.mcp_server.command` would AttributeError on `None`. `_load_config(allow_missing=False)` does always raise on missing, so the assert is purely documentation — but it would be safer as a runtime check that survives `-O`. Other call sites in the file follow the same pattern, so it's consistent.

**Fix:** Either accept the convention (it's used throughout the module) or replace with a typing.cast + comment:

```python
cfg = _load_config(config)
# _load_config(strict) returns Config or raises typer.Exit; safe to narrow.
assert cfg is not None  # nosec - documentation only
```

Better: use `typing.assert_type` or refactor `_load_config` into two functions, `_load_config_strict() -> Config` and `_load_config_or_none() -> Config | None`, so the type-narrowing is in the signature, not in operator-side asserts.

### IN-03: `test_state_resets_between_tests_part_a/b` test order is not guaranteed

**File:** `tests/framework/unit/test_tool_factory.py:106-118`
**Issue:** The pair-test for fixture isolation relies on pytest collecting tests in source order. pytest does collect in source order by default, but with parallelization (`pytest-xdist`) or randomization plugins (`pytest-randomly`) the pair can interleave with other tests or run in reverse, making `part_b`'s assertion meaningless. The `_reset_module_state` fixture (lines 30-38) is the real coverage; the pair test only proves "consecutive tests don't bleed" which the fixture already enforces.

**Fix:** Either delete the pair (the fixture is the contract) or replace with an explicit two-call function that mutates and reads state within one test:

```python
def test_module_state_isolated_between_tests() -> None:
    # Sentinel: this test should always see clean module state regardless
    # of preceding test ordering.
    assert tf._ACTIVE_SLUG is None or "test_slug" not in tf._REGISTRIES
```
