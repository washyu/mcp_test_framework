### Finding #2: SC#2 wrapper test FAILS on Windows due to `errlog` fileno limitation

`[VERIFIED: live reproduction]`

**What I did:** Ran the SC#2 test with the YAML overlay correctly set:
```
$ MCPTF_CONFIG_FILE=./config.yaml uv run pytest -m live_homelab tests/smoke/test_smoke_homelab_mcp.py::test_wrapper_call_tool_returns_non_error_with_content -v
```
Result: FAILED with this stack:
```
io.UnsupportedOperation: fileno
  in subprocess.py:1420 (Windows CreateProcess path)
  errwrite = msvcrt.get_osfhandle(stderr.fileno())
                                  ^^^^^^^^^^^^^^^
```
SC#1 (`test_raw_stdio_lists_target_tool`) which does NOT pass `errlog=` to `stdio_client` PASSES.

**Root cause:** `src/mcp_test_framework/mcp_client.py:62-91` defines `_LoggerWriter(io.TextIOBase)` and `mcp_client.py:116` wires it as `stdio_client(params, errlog=_LoggerWriter(_log))`. The SDK passes this through to `anyio.open_process(stderr=...)`, which on Windows lands inside `subprocess.Popen` calling `errwrite = msvcrt.get_osfhandle(stderr.fileno())` — Windows `CreateProcess` requires a real OS file descriptor, but `io.TextIOBase` has no fileno.

The `_LoggerWriter` docstring (`mcp_client.py:65-69`) states "The OS writes subprocess stderr bytes to write() on Windows and POSIX alike" — **this is incorrect for Windows.** The TextIOBase `.write()` API works only when the parent process owns the read end and pumps data manually; `subprocess.Popen` does not pump, it hands the fd to the child.

**This is D-07 absorb territory.** The fix is localized to `mcp_client.py`:
- The public `McpTestClient(command, args, timeout_seconds)` interface (D-08 lock) is unchanged.
- The `mcp_test_framework.mcp_client.stderr` logger contract (Phase 2 D-claude-discretion) can be preserved with a different plumbing.

**Two viable fixes (planner picks one, both are localized):**

| Option | What | Pro | Con |
|--------|------|-----|-----|
| **A: subprocess.PIPE + reader task** | Pass a pipe whose write end has a real fd to the SDK; spawn an asyncio task that reads the pipe and forwards each line to `_log.warning(...)`. | Preserves the stderr→logger contract verbatim. | More code (~30-50 lines), needs careful cleanup in `__aexit__`. |
| **B: drop `errlog=` and let stderr inherit** | Pass `errlog=sys.stderr` (a real fd-bearing object) OR just omit `errlog=` and accept the SDK default. | Smallest diff. The framework's pytest-driven users already get stderr surfaced via pytest's `-rA` capture. | Loses the logger-name handle (`mcp_test_framework.mcp_client.stderr`); `--log-cli-level=WARNING` no longer streams MCP stderr live. |

**Researcher's recommendation:** Option B for 02.1 (smallest diff, keeps the phase tight), with a note in the deferred-ideas log to revisit Option A in a future polish phase. The `_LoggerWriter` class can stay for unit-test backward compatibility (it has 2 unit tests) but is not wired to the SDK. Alternative: if the user prefers Option A's contract preservation, the plan grows by one task but the fix is still localized. The planner should surface this choice to the user during plan-phase rather than picking unilaterally.

**Escalation trigger NOT hit:** the public `McpTestClient` signature does not change; no new env vars; no config precedence change. Per CONTEXT.md D-07, this absorbs in 02.1.

## Common Pitfalls

### Pitfall 1: Forgetting `MCPTF_CONFIG_FILE` in pytest invocations

**What goes wrong:** Tests fail with `FileNotFoundError("MCP server command not on PATH: 'homelab-mcp'")`, planner mistakes this for a "real" SC#1 failure and tries to escalate.
**Why it happens:** Phase 1 locked "no cwd auto-discovery" for the YAML overlay; `Config()` defaults to the `.env.example` shape if neither shell env nor YAML overlay is present.
**How to avoid:** Every pytest task command in the plan MUST set `MCPTF_CONFIG_FILE=./config.yaml` (Bash) or `$env:MCPTF_CONFIG_FILE='./config.yaml'` (PowerShell).
**Warning signs:** Stack ends in `subprocess.py:1552: FileNotFoundError [WinError 2]` referencing `'homelab-mcp'` (not `'uvx'`). If you see `FileNotFoundError(... 'uvx')` THAT would be a real problem.

### Pitfall 2: Confusing the SC#2 errlog bug for an environmental issue

**What goes wrong:** Planner sees `io.UnsupportedOperation: fileno`, assumes Windows weirdness, asks the user to retry on Linux.
**Why it happens:** The `_LoggerWriter` docstring claims the API works on Windows and POSIX. It does not.
**How to avoid:** Recognize the stack signature: `subprocess.py:1420 ... errwrite = msvcrt.get_osfhandle(stderr.fileno())`. This is a deterministic Windows-side limitation of the chosen `errlog` shape, not flakiness. The fix is in `mcp_client.py` (D-07 absorb).
**Warning signs:** The error appears IMMEDIATELY (within ~0.5s of test start), well before any timeout — `1 failed in 0.61s`. A timeout-related failure would take 30s.

### Pitfall 3: Adding `config.yaml` to `.gitignore` AFTER staging it

**What goes wrong:** `git add .` includes `config.yaml`; later the gitignore line is added but git keeps the already-staged file.
**Why it happens:** `.gitignore` only affects untracked files; once tracked, `git rm --cached` is required to untrack.
**How to avoid:** D-09 (gitignore line) MUST land in a commit BEFORE any commit that runs `git add .`. Better: `git add` specific files by name (the GSD safety protocol already says this).
**Warning signs:** `git status` after the commit shows `config.yaml` as tracked.

### Pitfall 4: Glob caveats in `.gitignore`

**What goes wrong:** A bare line `config.yaml` could (in theory) match `subdir/config.yaml` too.
**Why it happens:** `.gitignore` patterns without leading `/` match at any depth.
**How to avoid:** For repo-root-only ignore, use `/config.yaml` (leading slash). For "any config.yaml in the tree", use `config.yaml`.
**Verified:** `git check-ignore -v config.yaml config.example.yaml` with `config.yaml` as a bare line in `.gitignore` returns:
```
.gitignore:22:config.yaml	config.yaml   ← MATCHES (correct)
                              ← no match for config.example.yaml (correct)
```
The bare line works correctly without affecting `config.example.yaml`. Either form (`config.yaml` or `/config.yaml`) is fine. Recommend `/config.yaml` for explicit-intent (defends against future submodule scenarios) but plain `config.yaml` matches the existing `.gitignore` style which uses bare names like `.env`.

### Pitfall 5: Line endings on the spec commit (D-10)

**What goes wrong:** `git config core.autocrlf=true` on Windows can cause LF→CRLF conversion in the working tree.
**Why it happens:** Default Windows `git` config.
**How to avoid:** Verified the spec file currently has LF-only line endings (`grep -c $'\r' docs/mcp_test_framework_mvp_spec.md` → 0). With `core.autocrlf=true` git will check OUT with CRLF (working tree) but COMMIT as LF — round-trip-safe. No special handling needed. **No `.gitattributes` exists** — also fine; the default behavior is correct here.
**Warning signs:** `git diff --check` after commit reports CRLF/LF whitespace issues. If it does, add `* text=auto eol=lf` to `.gitattributes` — but defer that to a future phase if it doesn't actually trip.

### Pitfall 6: Running both UAT pytest commands in the same shell without the env var persisting

**What goes wrong:** PowerShell session-scoped env vars don't survive across tool invocations if the planner uses one Bash command per task.
**Why it happens:** Each Bash invocation gets a fresh shell.
**How to avoid:** Either (a) inline the env var on each pytest invocation: `MCPTF_CONFIG_FILE=./config.yaml uv run pytest ...`, or (b) run both pytest commands inside the same task with `&&` chaining. Option (a) is cleaner for tasks per the GSD style.
**Warning signs:** The first test passes, the second fails with `FileNotFoundError('homelab-mcp')` — consistent with Pitfall 1.
