<decisions>
## Implementation Decisions

### Canonical run invocation

- **D-01:** The documented default invocation is `uvx homelab-mcp` (i.e., `MCP_SERVER_COMMAND=uvx`, `MCP_SERVER_ARGS=["homelab-mcp"]`). Rationale: zero-install for a fresh checkout — `uvx` is already required by the toolchain (`uv` is a hard dep) and `uvx` resolves the package, downloads it on first call, and runs it. Direct-binary invocation (`MCP_SERVER_COMMAND=homelab-mcp`) remains a valid alternative for users who have run `uv tool install homelab-mcp`, but is no longer the example default.
- **D-02:** Update three files to reflect D-01:
  - `.env.example` — change `MCP_SERVER_COMMAND=homelab-mcp` → `MCP_SERVER_COMMAND=uvx`; change `MCP_SERVER_ARGS=` → `MCP_SERVER_ARGS=["homelab-mcp"]`. Add a one-line comment above the block: `# Default invocation uses uvx for zero-install. To use a globally-installed binary, set MCP_SERVER_COMMAND=homelab-mcp and MCP_SERVER_ARGS=[].`
  - `config.example.yaml` — change `mcp_server.command: homelab-mcp` → `mcp_server.command: uvx`; change `mcp_server.args: []` → `mcp_server.args: [homelab-mcp]`. Same one-line comment.
  - `pyproject.toml` — change marker description from `"live_homelab: requires live homelab-mcp on PATH"` → `"live_homelab: requires homelab-mcp runnable via uvx (or on PATH)"`. The marker name and `addopts` skip behavior are unchanged.
- **D-03:** No change to `McpTestClient.__aenter__`'s `shutil.which()` pre-flight (Phase 2 D-08 / 02-CONTEXT). It still resolves whatever the user set as `command` — `uvx`, `homelab-mcp`, or any path. The `FileNotFoundError("MCP server command not on PATH: <name>")` diagnostic is sufficient; users who set `command=homelab-mcp` without `uv tool install` get a precise failure.

### UAT execution + result capture

- **D-04:** Run on developer machine (`config.yaml` already configured with `uvx` invocation). The two commands the planner must execute and capture verbatim:
  ```
  uv run pytest -m live_homelab tests/smoke/test_smoke_homelab_mcp.py::test_raw_stdio_lists_target_tool -v
  uv run pytest -m live_homelab tests/smoke/test_smoke_homelab_mcp.py::test_wrapper_call_tool_returns_non_error_with_content -v
  ```
  Pytest's stdout/stderr (the full `-v` block including PASSED/FAILED line and any traceback) gets pasted into `02-HUMAN-UAT.md` under each item, replacing the `result: [pending]` line with `result: passed` or `result: failed` plus a fenced code block of the captured output.
- **D-05:** "Phase 2 fully verified" trigger condition: BOTH tests pass on the same run, AND `02-HUMAN-UAT.md` summary fields go to `passed: 2 / pending: 0 / issues: 0`, AND `02-VERIFICATION.md` frontmatter is updated as listed in Phase Boundary item 3. Single source of truth for "Phase 2 done" is the verification frontmatter — the roadmap's `[x] Phase 2` checkbox is already set; that is now consistent.
- **D-06:** If a test FAILS, do NOT update `02-VERIFICATION.md` frontmatter. Instead: capture the failure into `02-HUMAN-UAT.md` with `result: failed` + the traceback, then proceed to D-07 (failure handling).

### Failure handling — when to absorb vs. escalate

- **D-07:** If a smoke test fails because of a real bug:
  - **Absorb in 02.1 IF** the fix is a localized config-, lifecycle-, or shape-handling change inside `src/mcp_test_framework/mcp_client.py`, `src/mcp_test_framework/config.py`, `src/mcp_test_framework/models.py`, or the test/example files. Examples: a stderr-buffer flush ordering bug, a `CallToolResult` shape branch we missed, a `shutil.which()` Windows-extension lookup edge case.
  - **Escalate to a new phase IF** the fix requires changing the `McpTestClient` public interface, adding new env vars, changing config precedence, or any cross-module refactor — i.e., anything that would re-open the Phase 2 spec or invalidate Phase 1 locks. Insert a new phase via `/gsd-insert-phase` and freeze 02.1 at "uncovered failing UAT, root cause documented".
- **D-08:** Document the trigger explicitly in the resulting plan: every plan that fixes a smoke-test failure must cite the failing test name, the captured traceback, and the chosen branch (absorb / escalate) with rationale.

### Doc + repo hygiene cleanups

- **D-09:** Add `config.yaml` to `.gitignore`. Rationale: `config.example.yaml` is the committed template; `config.yaml` carries machine-specific paths (uvx vs direct binary, custom Ollama URL on a different homelab, etc.). Currently NOT ignored (`git check-ignore config.yaml` returns nothing) — easy footgun via `git add .`.
- **D-10:** Commit the canonical spec `docs/mcp_test_framework_mvp_spec.md`. Currently untracked. Every CONTEXT.md, ROADMAP.md, and CLAUDE.md cites it as source-of-truth (e.g., `02-CONTEXT.md` line 93, CLAUDE.md "authoritative spec"). Without it in the repo, those references break for any fresh checkout. Commit verbatim from the working tree under `docs/mcp_test_framework_mvp_spec.md`. No edits in this phase — content is already locked upstream of any of our discuss/plan output.

### Claude's Discretion

The user did not specifically pick these — planner/executor has flexibility within the constraints below:

- **Order of operations within the phase:** the planner can sequence (a) doc/example reconciliation, (b) running UAT, (c) frontmatter updates, (d) gitignore + spec commit however makes sense. Suggested: do (a) and (d) first so a fresh `uv sync && cat config.example.yaml` reproduces the working setup, then (b), then (c) on green. But re-ordering is fine if the planner has a reason.
- **Plan granularity:** one plan or two plans is fine. Two natural slices are "doc/example/repo cleanup" (D-02, D-09, D-10) and "run UAT + flip frontmatter" (D-04, D-05). Single plan is acceptable if total work is small.
- **How the captured pytest output is formatted in `02-HUMAN-UAT.md`:** prose framing is up to the planner; minimum bar is the raw output is preserved and the summary fields tally. Use a `<details>` block if the traceback is long.
- **Whether to also update `02-VERIFICATION.md`'s "Items requiring human verification" prose section:** if frontmatter goes to `passed`, that section can be marked resolved with a one-line note pointing to the now-passed `02-HUMAN-UAT.md`. Planner's call.

- **README + Windows-troubleshooting notes** — Phase 5 DOCS-01 territory. The README currently exists only as a hatchling-build stub (Plan 02-01). Once Phase 5 lands, it should explicitly call out the `uvx homelab-mcp` default, the `live_homelab` marker, and Windows-specific cleanup (`taskkill /F /IM homelab-mcp.exe`).
- **CI workflow that runs the live_homelab marker** — Out of scope for MVP per PROJECT.md ("Solo project, local CLI for now. ... green CI = green local invocation."). When CI is added (post-MVP), the live tests need a `homelab-mcp` subprocess available in the runner — a meaningful infra prereq, not a framework change.
- **Richer `FileNotFoundError` diagnostic suggesting `uvx`** — If the user accidentally sets `MCP_SERVER_COMMAND=homelab-mcp` without `uv tool install`, the current error says "MCP server command not on PATH: 'homelab-mcp'". A future polish: append `". Try MCP_SERVER_COMMAND=uvx with MCP_SERVER_ARGS=['homelab-mcp']."`. Defer until a real user trips on it — premature ergonomics otherwise.
