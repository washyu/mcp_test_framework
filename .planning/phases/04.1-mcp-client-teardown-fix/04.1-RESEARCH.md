**Researched:** 2026-05-05

## Summary

CONTEXT.md locks the design (D-01..D-06): rewrite `mcp_client` fixture to use a single long-lived "owner task" spawned inside an outer `anyio.create_task_group()`, coordinated by two `anyio.Event` instances (`ready` + `shutdown`), so the task that opens `stdio_client`'s cancel scope is also the task that closes it. This pattern is **the canonical anyio recipe** — it appears verbatim in the anyio 4.13.0 `AsyncContextManagerMixin` documentation [CITED: anyio.readthedocs.io/en/stable/contextmanagers.html] and is the same shape recommended in the `MCPServer.run` thread of `PrefectHQ/fastmcp#348` and `modelcontextprotocol/python-sdk#521` [CITED: github.com/modelcontextprotocol/python-sdk/issues/521].

All 4 CONTEXT assumptions hold:

- **A1 (anyio.Event):** `[VERIFIED: .venv/Lib/site-packages/anyio/_core/_synchronization.py:82-97]` — `Event` class with `set()`, `wait()`, `is_set()` exists in anyio 4.13.0 (project-pinned via `mcp` transitive dep). Single-shot semantics (cannot be reused — must be replaced); fine for our once-per-session shutdown.
- **A2 (composition with pytest-asyncio session finalizer):** `[VERIFIED: anyio docs + practical pattern]` — `async with anyio.create_task_group()` inside an `@pytest_asyncio.fixture(loop_scope="session")` works because the task_group's cancel scope is entered AND exited inside the SAME `async def mcp_client()` generator coroutine, which pytest-asyncio drives end-to-end via `runner.run(async_finalizer())`. The fix moves the cancel scope INTO the fixture body itself rather than letting it bleed out via `AsyncExitStack` ownership of `stdio_client`.
- **A3 (cross-task session use):** `[VERIFIED: .venv/Lib/site-packages/mcp/client/stdio/__init__.py:117-118]` — `stdio_client` yields `read_stream, write_stream` which are `MemoryObjectReceiveStream`/`MemoryObjectSendStream` — anyio memory streams designed for inter-task communication. The cancel scope is on the task_group (line 183), NOT on the streams or the `ClientSession` instance. Tests calling `await session.list_tools()` from a per-test task while the owner task parks on `await shutdown.wait()` is safe by anyio design.
- **A4 (one owner task suffices):** `[VERIFIED: spec + existing fixture]` — fixture is `scope="session"`, single MCP subprocess per session. No per-test owner needed. Confirmed by reading existing `fixtures.py:168-185`.

**Primary recommendation:** Implement the owner-task pattern from §"Concrete Code Pattern" below. It's a ~30-line fixture body change. Drop `AsyncExitStack` from the fixture entirely — the owner task's `async with stdio_client(...) as ..., ClientSession(...) as session:` chain replaces it.

The critical invariant: the owner task's `async with stdio_client(...)` opens its `anyio.create_task_group()` cancel scope (`stdio/__init__.py:183`) and exits it WITHIN THE SAME OWNER TASK. The fixture task (`mcp_client` coroutine) only owns the OUTER `tg`, which IT enters and exits on a single coroutine — pytest-asyncio's `runner.run(async_finalizer())` calls `gen_obj.__anext__()` which resumes the same generator, so the outer `async with` enter/exit pair stays on the fixture-coroutine's task.

### Pattern 1: Owner-task with `anyio.Event` ready/shutdown coordination

**What:** Spawn a long-lived task that opens a context-manager chain, signals readiness, parks until shutdown, then unwinds the chain on the same task.

**When to use:** Any time you need an `async with X(...)` whose `__aenter__`/`__aexit__` must run on the same task, but the task that consumes `X` is different from the task that ran `__aenter__`. Specifically the case for any anyio context manager that opens a `task_group` internally (`stdio_client`, `sse_client`, `streamablehttp_client` — all MCP transports have this shape).

**Example:** See §Code Examples below.

### Pattern 2: `task_status.started()` (preferred anyio idiom for ready signaling)

**What:** Use `tg.start(_owner_task)` (note: `start`, not `start_soon`). The spawned task calls `task_status.started(value)`, which unblocks `tg.start()` and returns `value`. More idiomatic than a manual `anyio.Event` for ready (but you still need a separate `anyio.Event` for shutdown).

**When to use:** When the parent needs to receive a value from the spawned task (the live `client`/`session` handle) AND wait for setup completion atomically.

**Example:** See §Code Examples > "Variant B: task_status.started shape".

### Anti-Patterns to Avoid

- **`AsyncExitStack` owning `stdio_client` from the fixture body** — this is the current bug. The fixture body's stack is unwound by pytest-asyncio's finalizer, which runs `gen_obj.__anext__()` from a different task than the original enter. Drop the `AsyncExitStack` entirely from the fixture; the owner task's `async with` chain replaces it.
- **`McpTestClient.__aexit__` calling `await stack.aclose()`** — same root cause; `stack` was created on a per-test task during `__aenter__` but `__aexit__` runs from the finalizer task. After the rewrite, `McpTestClient` should NOT own an `AsyncExitStack` for `stdio_client`/`ClientSession`; the owner task owns that chain. The wrapper just holds a `ClientSession` reference.
- **Spawning a fresh `mcp_client` per test** — would multiply subprocess count by 10x and contradicts spec ("session-scoped"). Out of scope per CONTEXT.
- **Calling `tg.cancel_scope.cancel()` as the happy-path shutdown** — produces a `CancelledError` exit path that wraps in `BaseExceptionGroup` and pollutes diagnostics. Use `shutdown.set()` for the happy path (D-03).
- **`asyncio.Event` instead of `anyio.Event`** — works but breaks if the owner task is cancelled mid-`wait()`; anyio events integrate cleanly with cancel scopes (CONTEXT D-02).
- **Allowing the owner task to raise before `ready.set()`** — would deadlock the fixture on `await ready.wait()`. See §Code Examples for the error-propagation pattern (set ready in a `try/finally` OR wrap `ready.wait()` in `fail_after`).

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Cross-task signal | Bare `bool` flag + polling | `anyio.Event` | Polling busy-waits; Event integrates with cancel scopes |
| Wait for spawned-task ready | Sleep + retry | `anyio.Event.wait()` OR `tg.start()` + `task_status.started()` | Both are zero-overhead and respect cancellation |
| Hang protection | Manual loop with `time.monotonic()` | `anyio.fail_after(N)` (raises) or `anyio.move_on_after(N)` (silent) | Built-in, cancellation-aware, no manual bookkeeping |
| Subprocess termination | `subprocess.Popen.kill()` | `stdio_client`'s graceful stdin-close → SIGTERM → SIGKILL escalation | SDK already handles this (`stdio/__init__.py:191-212`); CONTEXT.md black-box rule applies |

**Key insight:** Every primitive needed for the owner-task pattern already ships in anyio 4.13.0. The fix is structural (move the cancel scope into the same task that exits it), not a new library.

## Common Pitfalls

### Pitfall A: Owner task raises before `ready.set()` → fixture deadlocks on `ready.wait()`

**What goes wrong:** If `stdio_client.__aenter__` fails (e.g., binary not on PATH, subprocess refuses to start), the owner task raises before reaching `ready.set()`. The fixture's `await ready.wait()` then blocks forever — pytest hangs until you Ctrl+C.

**Why it happens:** `task_group.__aexit__` propagates child-task exceptions only AFTER the `async with` block exits, but `await ready.wait()` is inside the block. Exception sits in the task_group's collected list, not visible to the parent yet.

**How to avoid:**
- **Recommended:** wrap the ready-wait in `anyio.fail_after(N)` so a hung handshake fails fast with `TimeoutError` (the owner task's real exception will surface from `task_group.__aexit__` shortly after).
- **Alternative (cleaner error propagation):** use `tg.start(_owner_task)` instead of `tg.start_soon(_owner_task)` — `tg.start()` blocks until either `task_status.started()` is called OR the spawned task raises, and re-raises the exception in the parent. This is the idiomatic anyio shape; see §Code Examples Variant B.

**Warning signs:** Test session hangs at "preflight check passed" with no further output; Ctrl+C reveals `await ready.wait()` in the traceback.

### Pitfall B: `shutdown.set()` runs but owner task is stuck inside `stdio_client.__aexit__`

**What goes wrong:** `shutdown.set()` wakes the owner from `await shutdown.wait()`, but the owner's `async with stdio_client(...)` cleanup is itself slow or hangs (e.g., subprocess refuses SIGTERM, requires SIGKILL). The fixture's outer `task_group.__aexit__` waits indefinitely for the owner.

**Why it happens:** `stdio_client/__init__.py:204` already wraps `await process.wait()` in `anyio.fail_after(PROCESS_TERMINATION_TIMEOUT)` — so within a few seconds the subprocess is force-terminated. But pre-2025 SDK versions might not, and the `await read_stream.aclose()` calls afterward have no timeout.

**How to avoid:**
- **Optional belt-and-suspenders:** wrap the entire fixture body's cleanup in a `move_on_after(N)` (recommended N=10s — generous since SDK already self-terminates in ~2s):
  ```python
  finally:
      shutdown.set()
      with anyio.move_on_after(10.0):
          # task_group.__aexit__ runs implicitly when we leave the `async with`
          pass
  ```
  But this is hacky — the `move_on_after` would have to be OUTSIDE the `async with task_group` block, which means restructuring. **Simpler:** trust the SDK's `PROCESS_TERMINATION_TIMEOUT` and accept that a truly hung subprocess produces a noisy timeout (better than silent zombie).

**Warning signs:** Pytest exits but Get-Process homelab-mcp returns matches; or pytest hangs for 30+s at session end.

### Pitfall C: pytest-asyncio plugin decorator confusion

**What goes wrong:** Mixing `@pytest.fixture` (sync) with `loop_scope="session"` — `loop_scope` is a `pytest_asyncio.fixture` parameter only.

**Why it happens:** The current `fixtures.py:46` uses `@pytest.fixture(scope="session")` for `config` correctly (it's sync); `fixtures.py:168` uses `@pytest_asyncio.fixture(loop_scope="session", scope="session")` for `mcp_client` correctly. The rewrite must preserve the `@pytest_asyncio.fixture(loop_scope="session", scope="session")` signature exactly.

**How to avoid:** Keep the existing decorator. Only the function body changes.

**Warning signs:** Collection errors like `ValueError: loop_scope is not a valid pytest.fixture argument`.

### Pitfall D: `pyproject.toml` config drift breaks the fix

**What goes wrong:** Phase 4 verified that `asyncio_default_test_loop_scope = "session"` does NOT fix the cancel-scope error (`04-03-SUMMARY.md` Failure B + speculative retry). It must remain `function` (the default — currently shown in the run output: `asyncio_default_test_loop_scope=function` per `04-03-RUN.txt:8`). The fix is fixture-body restructure, NOT a pyproject change.

**How to avoid:** Do NOT modify `pyproject.toml`'s `[tool.pytest.ini_options]` block. The current settings (`asyncio_mode="strict"`, `asyncio_default_fixture_loop_scope="session"`) are correct. Confirm by `grep -n asyncio_default_test_loop_scope pyproject.toml` returning empty.

**Warning signs:** Plan 04.1 includes a `pyproject.toml` change. Reject in code review.

### Pitfall E: `_preflight` parameter dropped from rewritten fixture signature

**What goes wrong:** Current signature is `async def mcp_client(config: Config, _preflight):`. The `_preflight` dependency is load-bearing — it ensures the MCP binary, Ollama, and target tool all exist before this fixture spawns its own session. Dropping `_preflight` from the parameter list breaks the dependency graph silently (autouse=True still fires `_preflight`, but `mcp_client` could spawn before `_preflight`'s checks complete).

**How to avoid:** Keep `_preflight` in the rewritten fixture's parameter list. Even though `_preflight` is `autouse=True`, the explicit dependency forces ordering.

**Warning signs:** `mcp_client` runs before preflight; preflight failure no longer aborts cleanly.

## Code Examples

### Variant A: Manual `anyio.Event` for ready (CONTEXT.md sketch — D-01 verbatim)

```python
# src/mcp_test_framework/fixtures.py — Phase 4.1 target shape (Variant A)
# Source: CONTEXT.md D-01 + anyio 4.13.0 docs (contextmanagers.html)
import anyio
import pytest_asyncio
from mcp import ClientSession
from mcp.client.stdio import StdioServerParameters, stdio_client


@pytest_asyncio.fixture(loop_scope="session", scope="session")
async def mcp_client(config: Config, _preflight):
    """Long-lived MCP session, owner-task pattern (Pitfall 1 fix).

    The owner task opens stdio_client + ClientSession, signals readiness,
    parks on `shutdown` Event, then unwinds. Cancel scope enter+exit happen
    inside the owner task — anyio's task-pinning rule satisfied.
    """
    shutdown = anyio.Event()
    ready = anyio.Event()
    holder: dict[str, McpTestClient] = {}
    error_holder: dict[str, BaseException] = {}

    params = StdioServerParameters(
        command=config.mcp_server.command,
        args=config.mcp_server.args,
    )

    async def _owner_task() -> None:
        # Cancel scope opens AND closes inside this task → no Pitfall 1.
        try:
            async with (
                stdio_client(params) as (read, write),
                ClientSession(read, write) as session,
            ):
                async with anyio.fail_after(config.mcp_server.timeout_seconds):
                    await session.initialize()
                # Hand the live session to the test fixture via the wrapper.
                holder["client"] = McpTestClient._wrap(session)
                ready.set()
                # Park until teardown signals shutdown.
                await shutdown.wait()
        except BaseException as exc:
            # Capture so the parent's ready-wait can re-raise.
            error_holder["exc"] = exc
            ready.set()  # unblock the fixture so it can surface the error
            raise

    async with anyio.create_task_group() as tg:
        tg.start_soon(_owner_task)
        # Bounded wait for owner readiness; surface owner-task errors fast.
        with anyio.fail_after(config.mcp_server.timeout_seconds + 5):
            await ready.wait()
        if "exc" in error_holder:
            raise error_holder["exc"]
        try:
            yield holder["client"]
        finally:
            # Owner wakes, unwinds stdio_client + ClientSession on its own task.
            shutdown.set()
        # Implicit: task_group.__aexit__ waits for owner to drain.
```

**Note on `McpTestClient._wrap`:** Per CONTEXT D-04 the wrapper's public API stays. The cleanest internal change: add a classmethod (or constructor flag) that builds an instance pre-bound to a live `ClientSession`, bypassing the current `__aenter__`/`AsyncExitStack`. The wrapper's `list_tools`/`get_tool`/`call_tool` methods stay; its `__aenter__`/`__aexit__` either become no-ops when used via `_wrap` OR are simply not called by the new fixture (it uses `_wrap` and never enters the wrapper as a CM). Planner's call. The session itself is safe to use from any task per A3.

### Variant B: `task_status.started()` shape (more idiomatic anyio)

```python
# Variant B — uses anyio's task_status.started() instead of a manual ready Event.
# Slightly cleaner error propagation: tg.start() blocks until either
# task_status.started() fires OR the owner task raises (and re-raises here).
import anyio
import pytest_asyncio
from anyio.abc import TaskStatus


@pytest_asyncio.fixture(loop_scope="session", scope="session")
async def mcp_client(config: Config, _preflight):
    shutdown = anyio.Event()
    params = StdioServerParameters(
        command=config.mcp_server.command,
        args=config.mcp_server.args,
    )

    async def _owner_task(*, task_status: TaskStatus[McpTestClient]) -> None:
        async with (
            stdio_client(params) as (read, write),
            ClientSession(read, write) as session,
        ):
            async with anyio.fail_after(config.mcp_server.timeout_seconds):
                await session.initialize()
            client = McpTestClient._wrap(session)
            task_status.started(client)  # unblocks tg.start, returns `client`
            await shutdown.wait()

    async with anyio.create_task_group() as tg:
        # tg.start() awaits task_status.started() OR re-raises owner errors.
        client = await tg.start(_owner_task)
        try:
            yield client
        finally:
            shutdown.set()
```

**Recommendation:** Variant B is preferred for new code (idiomatic anyio, automatic error propagation, fewer moving parts). Variant A matches CONTEXT.md's D-01 sketch verbatim — either is acceptable per CONTEXT's discretion language.
