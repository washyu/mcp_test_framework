<problem>
## Why the current fixture errors at teardown

**Symptom (verbatim from `04-03-RUN.txt`):**

```
ERROR at teardown of test_text_content_parses_as_json
...
File ".venv\Lib\site-packages\anyio\_backends\_asyncio.py", line 455, in __exit__
    raise RuntimeError(
RuntimeError: Attempted to exit cancel scope in a different task than it was entered in
```

**Mechanism:**

1. `mcp_client` fixture is `scope="session"`, `loop_scope="session"`. It opens `AsyncExitStack` and pushes `McpTestClient(...)` into it. Internally `McpTestClient.__aenter__` calls `mcp.client.stdio.stdio_client(...)`, which opens an `anyio.create_task_group()` (a cancel scope).
2. anyio enforces: the task that opens a cancel scope must be the task that closes it ("task pinning").
3. pytest-asyncio runs each `async def test_...` on a per-test task (default `asyncio_default_test_loop_scope=function`). When the session ends, pytest's session-finalizer machinery drives the fixture's teardown via `runner.run(async_finalizer())`, which spawns YET ANOTHER task to drive the unwind.
4. The teardown task is not the same task that originally entered `stdio_client`'s cancel scope → anyio raises `RuntimeError: Attempted to exit cancel scope in a different task than it was entered in`.
5. Side-effects observed: tests still PASS (all 10), the OS still cleans up the subprocess (`Get-Process homelab-mcp` after run = no matches → Windows SC#1 holds), but pytest exits non-zero because teardown ERROR is reported separately from test FAIL.

**Why the obvious config tweak doesn't fix it:**

Setting `asyncio_default_test_loop_scope = "session"` was tried (Phase 4 03-RUN-retry-fixed.txt — discarded). Same error in 15 s vs 25 s. That tells us the task mismatch is **finalizer-task vs fixture-yield-task within the same loop**, not loop-vs-loop. pytest-asyncio's session-finalizer is structurally a different task from the fixture-yield, even on a single session loop. Config can't fix it; the fixture body has to.

**Reference (research-trail):**

- `.planning/phases/04-fixtures-test-cases/04-RESEARCH.md` "Pitfall 1" (anyio task-pinning under pytest-asyncio session finalizers)
- `.planning/phases/04-fixtures-test-cases/04-CONTEXT.md` D-test10 family (already accepts that fixture-teardown semantics matter for SC#1)

<decisions>
## Implementation Decisions (locked at context-gather time; planner may refine within these bounds)

### D-01: Owner-task pattern with `anyio.Event` for graceful shutdown

The fixture spawns a single long-lived "owner task" inside an outer `anyio.create_task_group`. The owner task `__aenter__`s `stdio_client(...)` AND `ClientSession(...)`, signals readiness, parks on an `anyio.Event` until teardown signals shutdown, and then unwinds the contextmanagers — entry and exit both happen on the same task, satisfying anyio's task-pinning rule.

```python
# fixtures.py — Phase 4.1 target shape (illustrative; planner picks the exact API)
@pytest_asyncio.fixture(loop_scope="session", scope="session")
async def mcp_client(config: Config, _preflight):
    shutdown = anyio.Event()
    ready = anyio.Event()
    holder: dict[str, McpTestClient] = {}

    async def _owner_task():
        # Cancel scope opens AND closes inside this task → no Pitfall 1.
        async with stdio_client(...) as (read, write), ClientSession(read, write) as session:
            await session.initialize()
            holder["client"] = McpTestClient._wrap(session)
            ready.set()
            await shutdown.wait()  # park until teardown signals

    async with anyio.create_task_group() as tg:
        tg.start_soon(_owner_task)
        await ready.wait()
        try:
            yield holder["client"]
        finally:
            shutdown.set()  # owner wakes, unwinds stdio_client cleanly
```

### D-02: `anyio.Event` over `multiprocessing.Event` over `asyncio.Event`

- **`anyio.Event`** — chosen. Integrates with cancel scopes (a cancelled waiter raises cleanly), works under both asyncio and trio backends without conditional imports, native to the same library `stdio_client` already uses.
- **`multiprocessing.Event`** — rejected. Single-process problem; `multiprocessing.Event` creates an OS semaphore (~100× slower set/wait), pickles state, leaks on Windows in some test scenarios. No cross-process boundary exists in this codebase.
- **`asyncio.Event`** — viable but inferior to `anyio.Event` because anyio is already a transitive dep and the rest of the MCP SDK stack runs on anyio.

### D-03: Owner-task explicit cancellation is the failure-mode escape, not the happy path

Happy path is graceful Event signal → owner task exits its `async with`. If the owner task hangs (e.g., `stdio_client` never returns from `__aenter__`), the outer `task_group.__aexit__` will eventually run cancellation; the planner must handle that case but should not rely on cancel-as-shutdown.

### D-04: McpTestClient API surface unchanged

Tests still consume `client = mcp_client` and call `await client.list_tools()`, `await client.get_tool(name)`, `await client.call_tool(name, args)`. The fixture body changes; the wrapper class does not. If the wrapper currently owns its own `AsyncExitStack`, that internal lifecycle moves into the owner task or is replaced by direct `ClientSession` ownership — planner picks. Either way, no test in `tests/test_homelab_list_registered_servers.py` should need to change.

### D-05: Regression test added in Phase 4.1, not deferred

A small smoke test in `tests/smoke/` that:
- Spins up `mcp_client` fixture
- Issues at least one `list_tools()` call
- Lets the session end
- Asserts `pytest` exit code is 0 OR the test runs to its own teardown without raising the cancel-scope RuntimeError

This prevents future fixture reshuffles from silently re-introducing Pitfall 1.

### D-06: Acceptance is exit-code-zero, not just "10 passed"

Phase 4.1 is "done" when `uv run pytest tests/test_homelab_list_registered_servers.py` exits with code 0 against a live homelab-mcp + Ollama setup, AND `Get-Process homelab-mcp` after the run returns no matches. Today both halves fail/are inconclusive (exit non-zero; subprocess does clean up but only because the OS reaps it).

## Assumptions to validate during planning

- A1: `anyio.Event` is reachable from the project's already-pinned anyio version (it's been in anyio since 3.x; project pins anyio>=4.5 transitively).
- A2: pytest-asyncio's session-finalizer can drive a fixture that itself contains a `task_group` — i.e., the fixture body's `async with anyio.create_task_group()` will work under pytest-asyncio's outer event-loop runner. Believed yes (anyio task groups compose with asyncio loops via the asyncio backend), but planner should write a 5-minute spike before locking the fixture rewrite.
- A3: `McpTestClient._wrap(session)` (or equivalent) gives tests a stable handle that survives across the owner task's parked-on-Event lifetime. The session object itself is fine to use from any task; it's the cancel-scope on the *task group* that's pinned. Planner verifies.
- A4: No additional "owner task per test" granularity is needed — one session-scoped owner task serves all 10 tests. Confirmed by reading the spec ("one MCP server, one tool") and the existing fixture's `scope="session"`.
