<objective>
Implement the pure-data schema validator: a `ValidationIssue` Pydantic model (severity literal, JSON-Pointer path, message) and a `validate_tool_schema(tool: Tool) -> list[ValidationIssue]` function performing the 7 spec-defined deterministic structural checks. Auto-detect JSON Schema draft via `jsonschema.validators.validator_for`. Build paths from `error.absolute_path` (JSON-Pointer style), NOT `error.json_path` (JSONPath). Ship exhaustive unit tests proving each of the 7 checks fires correctly on synthetic tools and a fully valid tool returns the empty list.

Purpose: This module is consumed by Phase 4 TEST-02 only, but the contract (`severity`, JSON-Pointer `path`, `message`) ripples into `pytest` failure diagnostics. Phase 1 must lock this contract correctly the first time — the json_path vs absolute_path distinction (RESEARCH Pitfall 2) is the most common wrong turn.

Output: A pure function over `mcp.types.Tool` returning a typed issue list, plus passing tests covering all 7 checks.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `mcp.types.Tool` (subprocess output) → validate_tool_schema | The Tool object's contents originate from the MCP server (a black-box subprocess in later phases); inputSchema may be malformed/malicious |
| jsonschema's check_schema → ValidationIssue construction | jsonschema may raise on pathological schemas; must be caught |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-01 | Denial of Service | Maliciously deep / recursive inputSchema causes jsonschema.check_schema to recurse infinitely | accept | LOW for MVP — Phase 1 has no production input; the only schemas validated are from `homelab-mcp` (trusted) and synthetic test tools. Revisit if untrusted MCP servers are added |
| T-03-02 | Tampering | Bug in check ordering causes validate_tool_schema to raise instead of returning issues | mitigate | Pattern 4's structure: Check 3 wraps `check_schema` in try/except and returns issues list; later checks short-circuit on missing `inputSchema`. Acceptance test test_check_3_invalid_meta_schema verifies this path doesn't raise |
| T-03-03 | Information Disclosure | ValidationIssue.message leaks raw exception detail | accept | LOW — exception detail in dev/test diagnostics is desirable; no PII in JSON Schema content |
</threat_model>
