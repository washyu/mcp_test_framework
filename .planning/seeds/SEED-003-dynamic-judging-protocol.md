# SEED-003: Dynamic judging protocol — rubrics as data, not code

Replace the current static three-judge set (`description_clarity`,
`description_disambiguation`, `parameters_self_explanatory` — all hardcoded in
`src/mcp_test_framework/rubrics.py`) with a **dynamic rubric system** where
rubrics are first-class data: declarable in config, addressable by name,
versionable, comparable across runs, and potentially generated by an LLM rather
than hand-authored.

## Why This Matters

**Three forces converge on this:**

1. **Scaling judges across N tools.** Once v1.1 lands and the framework
   discovers N tools dynamically, running 3 fixed judges per tool means N×3
   Ollama calls per run with no way to dial down. Some tools don't need all
   three rubrics (`list_*` tools rarely have parameters worth grading); some
   need additional ones (e.g., destructive-action warnings, output-format
   suitability). Static judges force one-size-fits-all.

2. **Per-tool judge selection (raised in v1.1 design).** v1.1's per-tool config
   block is already shaping toward `judges: [clarity, disambiguation]` —
   meaning judges are **already becoming named entities referenced from
   config**. That's one short step from "rubrics are data." If v1.1 ships with
   string IDs that resolve to hardcoded Python rubrics, v1.2/v1.3 will need a
   migration; if v1.1 reserves the schema shape for rubric data, the migration
   is additive.

3. **Comparable scoring across runs and server versions.** Today a judge
   produces `score: 4` with no anchor — was that a 4 against today's rubric or
   yesterday's? If a maintainer tweaks the prompt, all historical scores
   silently shift. Versioned rubrics (`rubric_id: clarity@v2`) make scores
   comparable over time and across MCP server versions, which is exactly what
   CI/regression-testing needs.

A bonus, if explored: **LLM-generated rubrics** — given a tool's domain
(filesystem, network, auth, etc.) the judge model proposes the rubric set
before scoring. This collapses the "what should we even grade?" decision into
the eval pipeline itself. Worth a spike, not a commitment.

## When to Surface

**Trigger:** After v1.1 ships and at least one of these happens:
- Adding a new judge requires a code change (signal: judge growth is friction)
- Per-tool judge counts diverge significantly (some tools want 1, others want 5)
- A user or stakeholder asks "did this tool's score change because the tool
  changed or because we tweaked the rubric?"
- A milestone is opened that touches: rubric design, judge backend pluggability
  (PROJECT.md "Out of Scope"), evaluation strategy, scoring comparability

This seed should be presented during:
- `/gsd-new-milestone` when scope mentions: rubric, judge, evaluation,
  scoring, comparability, versioning, eval data, judge backend
- `/gsd-discuss-phase` for any phase that adds, modifies, or removes a judge
- Any planning that touches `src/mcp_test_framework/rubrics.py` or
  `src/mcp_test_framework/judge_protocol.py`

## Scope Estimate

**Large** — full milestone. The user explicitly flagged this in conversation
("really large change and could be its own milestone"). Concretely involves:

1. **Rubric data model.** A Pydantic schema for rubrics: id, version, system
   prompt, scoring contract, applicability rules (e.g., "only for tools with
   parameters"). Lives in config or a `rubrics/` directory.
2. **Rubric registry + resolver.** Loader that materializes rubric IDs into
   live `Judge` invocations, replacing the hardcoded `RUBRIC_*` constants in
   `src/mcp_test_framework/rubrics.py`.
3. **Per-tool rubric selection.** Already drafted as part of v1.1 config
   (`tools.<name>.judges: [...]`); v1.2 promotes those IDs from "names that
   match Python constants" to "keys into the rubric registry."
4. **Versioning and migration.** `rubric_id@version` addressing; deprecation
   path for retired rubrics; a way to run `clarity@v1` and `clarity@v2` side
   by side for comparison during a rubric change.
5. **Score history / comparability layer.** Optional but high-value: persist
   per-(tool, rubric_id, version) scores across runs so regressions are
   detectable. Probably JSON sidecar to JUnit output.
6. **Spike: LLM-generated rubrics.** Throwaway investigation — can the judge
   model propose rubrics from a tool schema? If yes, evaluate quality. If no,
   close the door and move on.

Each of these is a phase. Some may parallelize. Don't fold into v1.1.

  seam was deliberately built for exactly this kind of evolution.

  Dynamic rubrics don't change the backend; they change *what gets passed in*.
- **`src/mcp_test_framework/models.py`** — `JudgeResult` Pydantic model. May
  need a `rubric_id` and `rubric_version` field added when this seed
  germinates, to make scores self-describing.
- **`src/mcp_test_framework/config.py`** — config loader. Will gain a
  rubrics section parallel to whatever per-tool config v1.1 adds.
- **`tests/test_homelab_list_registered_servers.py`** — currently calls each
  rubric explicitly. With dynamic rubrics, the test layer parameterizes over
  resolved rubrics from config rather than naming each one in code.
- **`SEED-001-agentic-tool-use-judge.md`** — the agentic-judge seed proposes
  a *new judge backend*. SEED-003 is orthogonal: rubrics-as-data applies to
  *both* rubric-style and agentic backends (an agentic judge also needs a
  reflection rubric, which would benefit equally from being data not code).
  Likely both seeds germinate around the same milestone.
- **`docs/mcp_test_framework_mvp_spec.md` "Future Work"** — lists "Pluggable
  judge backends" as deferred. Dynamic rubrics is the *content* layer of that
  same direction (backends = how, rubrics = what).

## Notes

- **Critical interaction with v1.1:** when v1.1 designs its per-tool
  `judges: [...]` config field, it must use **string IDs that match the
  current rubric constants** (`clarity`, `disambiguation`, `parameters`)
  rather than embedding rubric content inline. That choice is what makes
  SEED-003 a non-breaking evolution rather than a v2.0-style migration. Flag
  this during v1.1's spec/discuss phase.
- **Versioning question for germination time:** does versioning live on the
  rubric (`clarity@v2`) or on the rubric *set* (a config-level snapshot
  hash)? Both have merit. Decide during the milestone, not now.
- **LLM-generated rubrics is the speculative wing.** Treat it as a spike, not
  a deliverable. If it works, great; if not, hand-authored data-rubrics
  alone is enough value to justify the milestone.
- **User intent (2026-05-06):** "looking at a more dynamic judging protocol
  rather than the current static 3 that we have… would be a really large
  change and could be its own milestone." Captured verbatim because the
  framing ("really large… own milestone") IS the trigger for treating this
  as deferred-but-deliberate, not as v1.1 scope creep.

## Vision-Pass Addendum (2026-05-07)

The `/gsd-explore` long-term-vision pass added a **fourth load-bearing dimension** to this seed's scope: **agent-realistic-mistake input fuzz testing.**

**Three agent-usability questions identified by the vision pass:**

1. Should I pick this tool right now? (description quality / disambiguation) — covered by current static rubrics
2. Can I construct a valid call? (schema clarity, parameter docs) — covered
3. **Does the tool handle inputs real agents send — including imperfect ones?** — **new in scope**

User framing (2026-05-07): "if the tools say string only for a parameter we can't assume the agent will always honor that … the llm agent use should be able to generate these kinds of test cases if asked when we add the dynamic style judging."

**Concrete implications:**

- **Input-generation rubrics become a first-class rubric category** alongside the current evaluation rubrics. An input-gen rubric takes a tool schema and produces N test calls — including imperfect ones an LLM agent might realistically emit (wrong types, missing fields, hallucinated parameter names, near-miss values). The framework runs those calls against the tool and observes the response behavior.
- **NOT a fuzzer in the adversarial sense.** Random adversarial input is anti-vision per PROJECT.md. *Agent-realistic-mistake* fuzz is in scope: it answers a vision-aligned question ("does this tool break when an agent makes a normal LLM-style mistake?"), not "does this tool crash on `\x00\xff\xff` payloads."
- **Collapses with the previously-distinct "test-input generation" deferral.** User clarification (2026-05-07): "test-input generation basically fuzz testing with extra test types." They are the same thing once an LLM is the generator. This seed absorbs both.

**Updated scope (additions to the original 6 components):**

7. **Agent-realism input-gen rubric type.** Rubric data shape that produces *test inputs* rather than scoring existing prose. Output: `(arguments_dict, expectation)` tuples where expectation ∈ {accept-and-parse, structured-error, undefined-behavior}.
8. **Tool-call-then-observe loop harness.** Run each generated input against the tool via `McpTestClient.call_tool`; classify each response (success / typed-error / crash / unparseable). The classification IS the eval signal.
9. **Reflection rubric over the call set.** After running all generated inputs for a tool, ask the judge to reflect on the result distribution and produce a `JudgeResult` with `passed/score/reasoning` shape.

**Cohort relationships:**

- **Depends on SEED-005 (v1.2).** The OpenAI-compat backend gives the judge access to structured-output primitives that materially simplify input-generation. Don't try to ship SEED-003 before SEED-005 lands.
- **Sequences before SEED-001 (v1.4+).** The agentic judge IS a richer version of the call-then-observe loop introduced here. Sequencing SEED-003 first means SEED-001's reflection layer has somewhere clean to live (rubric data) instead of being hardcoded.
- **Backend portability becomes a feature.** With SEED-005 in v1.2 and rubrics-as-data in v1.3, the framework can run the same rubric against the same tool via two different backends — exposing whether scores are model-dependent. Half the audit-secondary value prop comes from this comparability.

**Why scope stayed "Large" rather than bumping further:** the input-gen rubric type is a natural extension of the rubrics-as-data system, not an architectural new direction. The data model, registry, resolver, and versioning all generalize over input-gen rubrics for free. The marginal cost is the call-then-observe loop harness (component 8) — material but bounded.
